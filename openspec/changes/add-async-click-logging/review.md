### Findings

| 1 | major | design.md decision 4; tasks.md 2.1, 3.3 | `UnrecoverableMessageHandlingException` prevents retries, but does not prevent parking: the installed `SendFailedMessageForRetryListener` declines retry and `SendFailedMessageToFailureTransportListener::onMessageFailed()` then sends the envelope to `failed`. Thus every deleted-link message violates the promised first-attempt acknowledgement/discard and produces failure logging. Catch the FK failure outside the rolled-back transaction, log the specified info record and return normally (or specify another verified discard mechanism). Require a real Worker/listener-path test proving acknowledgement, no retry and no failed message; the proposed direct bus `consumeAsync()` helper cannot verify that lifecycle and currently throws for this case. Reconcile the applicability table and handler assertions. | open |
| 2 | major | design.md decision 2 and Applicability / Empty/zero/null inputs; specs/redirect/spec.md / Click limit is exact under concurrency | Re-enabling a limit reuses a stale existing key, contrary to the claim that unlimited-to-limited is seeded on the next redirect. Example: counter and persisted count are 3; clear `maxClicks`, serve and persist 4 unlimited redirects (count 7, key still 3), then set `maxClicks` to 10. With the worker paused, the script permits 7 more redirects instead of 3, without any key loss. The current update processor only changes the SQL field, and the plan adds no transition mechanism. Specify how retained counters account for unlimited-period clicks, including queued clicks and concurrent limit changes, and add transition implementation and verification tasks. Any weaker guarantee must be explicit and reconciled with the requirement. | open |
| 3 | major | proposal.md item 2; design.md decision 2 and Risks; specs/redirect/spec.md / Click limit is exact under concurrency | The claimed overshoot bound of only the queue backlog at seeding time excludes redirects whose dispatch failed. For max 3, allow three redirects while the counter works but dispatch throws: key 3, persisted count 0, backlog 0. Lose the counter key and the next redirect seeds 0 and allows three additional redirects, exceeding the limit with no backlog. Crashes before dispatch and messages parked after permanent failure also leave increments outside the stated backlog. Define the actual bound in terms of unpersisted accepted increments (and repeated loss), or provide a mechanism that enforces the stronger claim; add a failure-plus-key-loss scenario and reconcile FR-RED-3 and the planned operational documentation. | open |
| 4 | major | tasks.md 3.3 / retry then park fallback | The optional fallback to testing `MultiplierRetryStrategy` and reading configuration does not verify the promised retry-to-failed lifecycle or demonstrate a failing input when failure routing is removed. Such a test can pass with missing Worker event subscribers or broken parking. Make a Worker test with the configured retry/failure listeners mandatory (in-memory transports can exercise the event flow without waiting for real delays), asserting four handler attempts, retry stamps/delays, one failed envelope and unchanged click data; require it to fail when routing to the failed transport is disabled. | open |
| 5 | minor | tasks.md 1.2 / migration verification | `make console ARGS='dbal:run-sql "\d messenger_messages"'` cannot inspect the table: `\d` is a psql meta-command, while the installed DBAL RunSqlCommand passes its argument to the database as SQL. Replace it with an executable catalog query or an explicit psql invocation before recording this task as verified. | open |
