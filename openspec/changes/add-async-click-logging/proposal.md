# Proposal — add-async-click-logging

**Risk-Tier:** high

Tier rationale (roadmap row 7, NFR-SEC-7, AGENTS.md triggers): Messenger retry and failure-transport behaviour; concurrency of the click limit moved to a Redis counter under concurrent first redirects and key loss; a delete-then-consume race on `clicks`; a new migration (the `failed` queue table). Gate 1 + Gate 2, a demonstrated failing input for every new guard, a green branch run before Gate 2 (auto review mode).

## Why

The redirect still writes the click synchronously — one `UPDATE` and one `INSERT` inside the request — which the stage-1 baseline accepted on purpose and the brief forbids for the final hot path (FR-RED-2: at most one `SELECT`, no SQL write; FR-RED-4: the redirect never waits for or fails on logging). Every redirect currently contends on the `links` row lock and depends on PostgreSQL's write path; a slow database slows every visitor. This change moves the click write behind Symfony Messenger on the Redis Streams transport that is already configured, makes the Redis counter the authority for the click limit, and keeps the redirect's observable contract — the 404/410/302 matrix, exact limits, the failure policies — while the row lands in `clicks` a moment later through a worker. It is the last change before the analytics read model (row 8) reads what the worker writes.

## What Changes

1. **Redirect performs no database write** (FR-RED-2): `ClickRecorderInterface` — the seam the previous two changes built — gets a Messenger implementation. The redirect does one `SELECT` (the link by slug), for a limited link one Redis command (the counter of item 2), and dispatches one `ClickRecorded` message. No `INSERT`, no `UPDATE`. A Web test asserts the statement kinds executed during a redirect. The synchronous `DbalClickRecorder`, its integration test and its child-process fixture are removed — the seam has exactly one implementation again.
2. **Redis counter is the limit authority** (FR-RED-3): for a link with `maxClicks`, one `EVAL` of a fixed Lua script against `link:{id}:clicks` (the script body is sent every time — no `EVALSHA`/`NOSCRIPT` round trip) which, atomically, seeds the key from `links.click_count` when absent, compares with `max_clicks`, increments only when allowed, and answers `allowed | exhausted`. Exhausted → 410 before any message is sent. Links without `maxClicks` never touch Redis. The script lifts a key that is absent or below the persisted `click_count` to that count on every call and never lowers it, so a limit set or changed after an unlimited period takes effect on the next redirect with no extra hook. Guarantee boundary stated in the spec and reconciled in FR-RED-3: the limit is exact while the key exists; whenever the key is seeded or lifted the seed excludes every accepted redirect not yet persisted (queued, dispatch-failed, parked, crashed before dispatch), so the limit may be exceeded by at most that many per seeding, plus the requests in flight at a limit change (each redirect evaluates the link row it loaded and never re-reads it), compounding with repeated key loss. Redis persists with AOF in the Compose stack. The key is removed when the link is deleted.
3. **`ClickRecorded` message and handler** (FR-CLK-1…4): an immutable message carrying the finished click row — `click_id` (UUID v7, the future primary key), link id, `occurred_at`, the routing facts (`country`, `device_type`, `os`, `browser`, `is_bot`, `resolved_by`, `variant`), `referer_host` and `visitor_hash`. The handler inserts the row and increments `links.click_count` in one transaction. Idempotency by construction: a redelivered message hits the primary key, the transaction rolls back and the message is acknowledged without a second increment. **The message carries no raw IP or user agent**: detection, geolocation and hashing already happen in the request (they are needed for routing since `add-routing-rules`), so putting the raw values on the queue would only widen where personal data sits (NFR-SEC-6). The brief's FR-CLK-1/2 wording ("the handler derives …") is updated in this change to say so.
4. **Retries and the failed transport** (FR-CLK-5, NFR-REL-2): handler failures are retried 3 times with exponential backoff (exactly 1 s, 2 s, 4 s — the configured strategy gains `jitter: 0`; FrameworkBundle's default of 0.1 would randomise the delays) and then routed to the `failed` Doctrine transport (`messenger_messages`, created by a reviewed, reversible migration; `auto_setup` off). Exception: a message whose link no longer exists (deleted after the redirect) fails the foreign key on insert; the handler catches that outside the rolled-back transaction, logs `info` and returns, so the worker acknowledges it on the first attempt — never retried, never parked (an unrecoverable exception would still be parked by Messenger's failure listener). Both lifecycles — retried then parked, acknowledged on the first attempt — are proven by tests that run a real Worker over the in-memory transports; the delete-then-consume race is one of them.
5. **Failure contract of the redirect, final form** (FR-RED-3/4, NFR-REL-1): link lookup failure → 503 for every slug (unchanged). Counter unavailable (Redis down or the script fails) for a link **with** `maxClicks` → 503 with `Retry-After: 5`, logged at `warning` — the limit cannot be guaranteed; a link **without** `maxClicks` is unaffected because it never calls Redis. Dispatch failure (transport down) after the counter accepted → 302 for every link and an `error` record; the redirect never waits for or fails on logging. A crash between the counter's increment and the dispatch leaves one counted click without a record — bounded to one per crash, stated. `HEAD` is unchanged: no counter, no message.
6. **Eventual consistency made explicit**: `clickCount` in link responses is maintained by the handler and lags by the queue backlog (FR-LNK-11); the specs say so, and the Web tests consume the in-memory transport before asserting rows and counts.
7. **Tests** (exit criterion of §7 row 7): no SQL write on redirect (statement kinds asserted through a test-only DBAL middleware); redelivery of the same message → one row, one increment; transport down → 302 and an `error` record, no row; counter down → 503 for a limited link, 302 for an unlimited one that never touched Redis; deleted-link message through a real Worker → acknowledged on the first attempt, not retried, not in `failed`, `info` record; a persistently failing message through a real Worker → four attempts with the configured backoff stamps, parked on `failed` once, and the test fails when the failure transport is disabled; concurrent first redirects on a fresh key (ten processes) → exactly `max_clicks` allowed and the key seeded once; seeding from a non-zero `click_count`; a limit re-enabled after unlimited redirects lifts the key to the persisted count; dispatch failures followed by a key loss reproduce exactly the stated overshoot; the Redis Streams transport round-trips a message (integration, real Redis); the migration is reversible; every existing redirect, click-logging and routing scenario still holds with the transport consumed in the test.
8. **Docs**: the how-to's Redirect section loses the stage-1 baseline note and gains the async flow (worker required, `make worker` / the compose profile, `messenger:stats`, `messenger:failed:show|retry` runbook, Redis-down behaviour, the counter key and its seeding, the deletion of the key with the link); `docs/explanation/requirements.md` FR-CLK-1/2 reworded (message carries facts, never raw IP/UA) and FR-RED-3's overshoot bound restated as unpersisted accepted increments; roadmap row 7 and §7 row 7 re-read against the delivered scope.
9. **No new dependencies**: `symfony/messenger`, `symfony/redis-messenger`, `symfony/doctrine-messenger`, `ext-redis` and `symfony/cache` (whose Redis connection factory builds the counter client from `REDIS_URL`) are installed; the transports, retry strategy and consumer naming are already configured in `config/packages/messenger.yaml`.

## Capabilities

### New Capabilities

None. Asynchronous logging changes *how* the existing `redirect` and `click-logging` guarantees are met and adds requirements to them; it introduces no new user-facing capability.

### Modified Capabilities

- `redirect`: "Click limit is exact under concurrency" — the Redis counter as the authority, seeding and its guarantee boundary; "Failures of the stores" — counter failure vs. dispatch failure policies, no SQL write; "Public redirect endpoint" — the HEAD scenario's wording (no counter, no message); ADDED "The redirect performs no database write".
- `click-logging`: "One click per successful redirect" — the record arrives through the queue, exactly once by idempotent handling, `clickCount` eventually consistent; "Clicks follow their link on deletion" — the counter key is removed and queued messages for the link are discarded; ADDED "Click messages are handled idempotently", "Failed messages are retried, then parked", "Messages for deleted links are discarded", "The queue carries no raw personal data".
- `links`: "Read and list own links" — `clickCount` is eventually consistent; "Delete a link" — the Redis counter is removed with the link.

## Non-goals

- Analytics reports, the report cache and its invalidation (`add-analytics-read-model`, row 8) — this change only produces what row 8 reads.
- Performance measurement of the hot path and the worker (NFR-PERF-1/3) with documented `wrk`/`ab` commands and numbers — `harden-quality-and-docs` (row 13, README benchmarks); this change removes the SQL write that made the measurement pointless.
- Partitioning or retention of `clicks` (stretch), a `click_daily` aggregate (stretch).
- A second consumer group, message priorities, a dead-letter UI beyond `messenger:failed:*`, alerting; horizontal scaling of workers beyond the compose profile (workers name themselves by hostname already).
- Changing the message serializer (Messenger's default PHP serializer is used; the queue is private to this application), encryption of the stream, or a Redis Cluster.
- Rebuilding `links.click_count` from `clicks` (no drift is expected: one transaction per message); a repair command is a future change if drift is ever observed.
- Link caching for redirects during a PostgreSQL outage (the link lookup still needs the database; 503 for every slug stands).
