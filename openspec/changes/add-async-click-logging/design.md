# Design — add-async-click-logging

## Context

See `proposal.md` — Why. State: `ClickRecorderInterface::record(Link, Visit, ClickFacts): RecordOutcome` is the seam; its only implementation, `DbalClickRecorder`, runs one transaction (conditional `UPDATE links … WHERE click_count < max_clicks`, then `INSERT clicks`) and `RedirectResolver` maps a thrown recorder failure to 302 + `error` for an unlimited link and 503 + `warning` for a limited one; `ClickFacts` already carries country, device, OS, browser, bot flag, `resolved_by` and variant because routing needs them in the request; `VisitorHasher` and `RefererHost` compute the hash and the referer host from the `Visit`; `clicks.id` is a UUID primary key and `links.click_count` has no setter on the entity. `config/packages/messenger.yaml` already defines the `async` Redis Streams transport (stream `messages`, group `linkboard`, consumer = hostname, retry 3× / 1 s / ×2), the `failed` Doctrine transport and `failure_transport: failed`, with both transports `in-memory://` under `when@test`; `routing` is empty. `REDIS_URL` feeds the rate-limiter pool and the lock store; `HealthProbe` builds its own ext-redis client from the same URL; `symfony/cache`'s `RedisAdapter::createConnection(string $dsn)` returns a configured `\Redis`. The Compose stack runs Redis with AOF and offers a `worker` profile (`messenger:consume async`). `.env.test` is committed; CI sets `MESSENGER_TRANSPORT_DSN=in-memory://`, `REDIS_URL` and `LOCK_DSN` to a service container. Constraints: no new dependency; the seam and the resolver's failure mapping stay; Click must not depend on Redirect; no Redis on the hot path for unlimited links beyond the fail-open limiter; level-8 PHPStan; migrations reversible.

## Goals / Non-Goals

**Goals:** a redirect with one `SELECT`, at most one Redis command and one dispatch; the limit enforced by one atomic Redis script with a stated guarantee boundary; a handler that is idempotent by construction and discards orphans without retries; the failed queue backed by a migrated table; every existing redirect/click/routing scenario still green with the transport consumed in tests; the synchronous recorder gone.
**Non-Goals:** see proposal. Design-level: no repair of `click_count` from `clicks`; no caching of links; no message versioning (one producer, one consumer, same deploy); no per-message deduplication store beyond the primary key; no TTL on counter keys (deleted with the link); no change to the resolver's decision order or its log records.

## Decisions

1. **The seam keeps its shape; the recorder becomes `MessengerClickRecorder`** (`src/Click/Recorder/`). `record(Link $link, Visit $visit, ClickFacts $facts): RecordOutcome`: (a) if `$link->getMaxClicks()` is not null → `$this->counter->increment($link->getId(), $link->getClickCount(), $max)` (decision 2); `Exhausted` → return `Exhausted` (410, nothing dispatched); a throwable from the counter **propagates** — the resolver's existing mapping turns it into 503 + `warning` for exactly this case (limited link, spec "Click write fails for a limited link"); (b) build `ClickRecorded` (decision 3) and `$this->bus->dispatch($message)`; a throwable from the dispatch is **caught here**: `error('Click message not dispatched; redirect served anyway', ['link_id', 'exception' => class])` and `return RecordOutcome::Allowed` — for limited and unlimited links alike, because the limit was already enforced by the counter and FR-RED-4 says the redirect never fails on logging. The resolver's write-failure branch therefore only ever sees counter failures. `RedirectResolver` changes in its docblock only; `config/services.yaml` rebinds `ClickRecorderInterface` to the new class; `DbalClickRecorder`, its test and `tests/Fixture/record-click.php` are deleted (`rg DbalClickRecorder` empty). Alternative — dispatch first, count later in the handler — rejected: the limit would lag by the backlog and FR-RED-3 makes the counter the authority at redirect time. Alternative — let dispatch failures propagate and special-case them in the resolver — rejected: the resolver would need to know two failure classes of one seam; the recorder is the place that knows which step failed.
2. **Counter: `ClickCounterInterface` + `RedisClickCounter`** (`src/Click/Counter/`). `increment(Uuid $linkId, int $seed, int $max): RecordOutcome`; `forget(Uuid $linkId): void`. One `\Redis` client from `RedisAdapter::createConnection(REDIS_URL)` (the same factory the limiter pool and the tests already use), created lazily on first use and kept for the process; every increment is one `$redis->eval(self::SCRIPT, [$key, $seed, $max], 1)` — `EVAL` with the script body every time, never `EVALSHA`, so a script-cache flush after a Redis restart costs no second round trip (FR-RED-2/3). Script:
   ```lua
   local seed = tonumber(ARGV[1])
   local current = tonumber(redis.call('GET', KEYS[1]))
   if current == nil or current < seed then redis.call('SET', KEYS[1], seed); current = seed end
   if current >= tonumber(ARGV[2]) then return 0 end
   redis.call('INCR', KEYS[1])
   return 1
   ```
   Seed, compare and increment run atomically inside Redis, so N concurrent first redirects on an absent key seed it once and let exactly `max` through (tested with ten child processes, `tests/Fixture/count-click.php`). **The counter is never below the persisted count**: every call passes the link's persisted `click_count` as the seed and the script lifts a lower or absent key to it. This is what makes a limit change safe without any hook: a link that was unlimited (its key untouched or absent while clicks were persisted) and becomes limited is lifted to the persisted count on its next redirect; a stale key left by a failed cleanup heals the same way; a raised or lowered `maxClicks` is simply the new `ARGV[2]` on the next call (Gate 1 finding 2). The script never lowers a key, so the redirects accepted during an unlimited period that are still queued — and therefore not yet in `click_count` — are the only ones the lift can miss; that is the same bound as below. **Snapshot semantics across a limit change** (Gate 1 confirmation finding 2): a redirect evaluates the `maxClicks` and `click_count` it read in its single `SELECT`; nothing re-reads the row or synchronises with a concurrent `PATCH`. A request that loaded the link before a limit change therefore completes under the limit it loaded — an unlimited snapshot never consults the counter, a snapshot with a higher maximum may increment past a lowered one — and a request that loads the link after the change commits sees the new limit at once. The number of such requests is bounded by the requests in flight at the moment of the change (a request-duration window), every one of them dispatches its message, and once persisted their clicks are counted twice over: the resolver's fast path answers 410 from the persisted `click_count` as soon as it reaches `max_clicks` (without consulting the counter, whose key then stays where it was), and the counter itself is lifted to the persisted count on the next call that reaches it (for instance after the limit is raised). The transition overshoot is therefore at most the in-flight count and stops as soon as those clicks are persisted. Alternative — synchronising the limit through Redis (storing `max_clicks` next to the counter and updating it on `PATCH`) — rejected: unlimited redirects would have to consult Redis to notice a change, adding a hot-path dependency for every link, and the `PATCH` would depend on Redis; the request-duration window is stated instead and verified by a controlled interleaving through the recorder seam (task 2.2). Key: `<prefix>link:<uuid>:clicks`, no TTL; `$prefix` is a constructor argument, `''` in dev/prod (the key of §3.5) and `test:` under `when@test` so the test suite can `SCAN`/`DEL` `test:link:*:clicks` on a Redis it shares with the dev stack without touching dev counters. A `\RedisException` or a non-integer script reply propagates as `\RuntimeException` — the recorder lets it through (decision 1). `forget()` is `DEL`. Guarantee: the limit is exact while the key exists and reflects every accepted redirect since the key was last seeded. Not guaranteed — the **overshoot bound**, stated in the spec and in FR-RED-3 (task 4.2): whenever the key is absent or below the persisted count (first redirect of a limited link, a limit change after an unlimited period, a Redis data loss), the seed is the persisted `click_count`, which excludes every *accepted increment that has not been persisted yet*: messages still queued, messages whose dispatch failed (302 without a record), messages parked on `failed`, and crashes between the increment and the dispatch. The limit may therefore be exceeded by at most that number of unpersisted accepted increments per seeding, plus the requests in flight at a limit change (snapshot semantics above), and repeated key loss compounds it. `clicks` remains the exact record of what was persisted; the analytics stage reports from it. Redis AOF in Compose makes loss exceptional (Gate 1 finding 3). Alternative — seed from `SELECT count(*) FROM clicks` — rejected: a SQL read on the hot path only when the key is absent would still be a second query and no more current than `click_count`. Alternative — `INCR` + compare in PHP — rejected: two round trips and a race between them.
3. **`ClickRecorded` message** (`src/Click/Message/ClickRecorded.php`, readonly, scalars only — `services.yaml` already excludes `src/*/Message/` from the service scan): `clickId` (UUID v7 string, generated in the recorder — the future primary key), `linkId`, `occurredAt` (`\DateTimeImmutable`), `country`, `deviceType`, `os`, `browser`, `isBot`, `resolvedBy`, `variant`, `refererHost`, `visitorHash`. The recorder computes `visitorHash` (`VisitorHasher`) and `refererHost` (`RefererHost`) from the `Visit` in the request — both are already injected into the current recorder — so the message never carries the IP, user agent or header values (spec "The queue carries no raw personal data"; a Web test asserts the serialized envelope). Detection and geolocation are not repeated in the worker: they already ran for routing. This is a deliberate deviation from the letter of FR-CLK-1/2 ("the handler derives …"), which predates routing on the hot path; task 5.2 rewords the brief. Messenger's default PHP serializer is used (one application on both ends; the stream is private) — stated as a non-goal to change. `messenger.yaml` gains `routing: App\Click\Message\ClickRecorded: async`.
4. **`ClickRecordedHandler`** (`src/Click/Handler/`, `#[AsMessageHandler]`, depends on the DBAL `Connection` and a logger; no entities — CQRS-lite, the write path never hydrates). One `transactional()`: `INSERT INTO clicks (id, link_id, occurred_at, country, device_type, os, browser, is_bot, referer_host, visitor_hash, variant, resolved_by)` then `UPDATE links SET click_count = click_count + 1 WHERE id = :id`. The insert goes first so the constraints decide the outcome before any increment: `UniqueConstraintViolationException` (same `click_id` again — a redelivery or a manual retry) → the transaction is rolled back, the handler logs `debug` and returns normally (the message is acknowledged; one row, one increment — spec "Click messages are handled idempotently"); `ForeignKeyConstraintViolationException` (the link is gone — deleted after the redirect, FR-LNK-10) → caught **outside** the rolled-back transaction, the handler logs `info` `{link_id, click_id}` and **returns normally**, so the worker acknowledges the message on its first attempt — no retry, no parking. `UnrecoverableMessageHandlingException` is deliberately not used: the installed `SendFailedMessageForRetryListener` declines the retry for it, but `SendFailedMessageToFailureTransportListener::onMessageFailed()` then parks every non-retried failure on `failed`, which would turn every deleted link into a parked message with failure logging (Gate 1 finding 1; verified in `vendor/symfony/messenger/EventListener/`). Any other throwable propagates → retry strategy → `failed`. The lifecycle claims — acknowledged, not retried, not parked; retried three times then parked — are proven by tests that run a real `Worker` over the in-memory transports with the container's event dispatcher (decision 7), not by the direct-bus helper. Insert-first also removes the need for a `SELECT … FOR UPDATE` on the link: the FK is the existence check and the `UPDATE` by primary key never touches a row that vanished (the FK failure came first). Alternative — pre-check `SELECT 1 FROM links` — rejected: a race between the check and the insert, and one more statement per click.
5. **Failed transport table by migration** — `messenger.yaml`: `failed: { dsn: 'doctrine://default?queue_name=failed', options: { auto_setup: false } }`. `make migration` picks the table up through the bridge's `MessengerTransportDoctrineSchemaListener` (verified present in `vendor/symfony/doctrine-bridge/SchemaListener/`); the generated class is reviewed: `messenger_messages` with the bridge's columns and indexes, `getDescription()`, reversible `down()`. The test environment keeps `in-memory://` for both transports; the table still exists in the test database because the schema comes from migrations (harmless). Alternative — `auto_setup: true` — rejected: DDL from a request or a worker at runtime (NFR-REL-3 wants migrated schema).
6. **Redirect resolver unchanged; delete processor removes the counter** — `RedirectResolver` keeps its order and log records (the write-failure branch now documents "counter failure"). `DeleteLinkProcessor` calls `ClickCounterInterface::forget($linkId)` **after** the flush, inside `try/catch (\Throwable)` → `warning('Click counter key not removed', ['link_id', 'exception' => class])`; the deletion is committed either way (spec "Redis down at deletion"). An orphaned key is harmless: no link references it, it has no TTL, and a new link never reuses a UUID. Queued messages for the deleted link are discarded by decision 4.
7. **Tests: the transport is consumed explicitly, lifecycles through a real Worker** — `RedirectWebTestCase` gains `consumeAsync(): int` which runs `Symfony\Component\Messenger\Worker` over the in-memory `messenger.transport.async` with the container's `messenger.default_bus` and `event_dispatcher` (so the configured retry, failure-transport and ack listeners are in play) and a `StopWorkerOnMessageLimitListener` sized to the pending count — this is the same code path as `messenger:consume`, so it can assert acknowledgement (`getAcknowledged()`), rejection, redelivery stamps and the `failed` in-memory transport; `pendingMessages(): list<Envelope>` reads `getSent()`; the in-memory transport honours `DelayStamp` through its clock, so `when@test` sets the `async` retry strategy to `delay: 10` (ms) with the same `max_retries: 3` and `multiplier: 2`; the retry strategy sets `jitter: 0` in every environment — FrameworkBundle defaults it to 0.1 and `MultiplierRetryStrategy` applies it with `random_int`, which would make the backoff 1 s / 2 s / 4 s of FR-CLK-5 approximate and the test's delays flaky (Gate 1 confirmation finding 4). The lifecycle test finishes in well under a second and asserts: four handler attempts (a counting decorator), three `WorkerMessageRetriedEvent`s whose envelopes carry `DelayStamp`s of exactly 10, 20 and 40 ms and `RedeliveryStamp` retry counts 1, 2 and 3, and exactly one envelope on the in-memory `failed` transport — whose *last* `RedeliveryStamp` is the parking stamp `SendFailedMessageToFailureTransportListener` appends with retry count 0, so the retry count is read from the retry events, not from the parked envelope. The production values 1000 / 2 / 3 / jitter 0 are asserted from `debug:config framework messenger` in the dev environment; `redis(): \Redis` from `REDIS_URL` and a `tearDown` that `SCAN`s and deletes `test:link:*:clicks`. Existing Web tests that assert rows or `clickCount` call `consumeAsync()` first; the "before the worker runs" scenarios assert the queue instead. Degradation stubs: the counter is replaced through the test container (`getContainer()->set(RedisClickCounter::class, throwing stub)` — it is lazily constructed, so replaceable, unlike the boot-time chain of the previous change); the transport is replaced by a `TransportInterface` whose `send()` throws (`messenger.transport.async`). The counter race: `tests/Fixture/count-click.php` runs `RedisClickCounter::increment()` on a fresh key from ten processes (the previous change's child-process pattern). The Redis Streams transport itself is covered by an integration test that builds `Symfony\Component\Messenger\Bridge\Redis\Transport\Connection::fromDsn(REDIS_URL, ['stream' => 'messages_test_<random>', 'group' => 'test', 'consumer' => 'phpunit'])`, `add()`s a serialized `ClickRecorded`, `get()`s it back, `ack()`s and `cleanup()`s — the only test that touches a real stream; every other test uses `in-memory://`.
8. **"No SQL write" is asserted, not assumed** — a test-only DBAL middleware (`App\Tests\Fixture\StatementRecorder`, implementing `Doctrine\DBAL\Driver\Middleware`, registered under `when@test` with the `doctrine.middleware` tag) records every executed SQL string in a static list the Web test resets before the request and reads after it: exactly one statement starting with `SELECT` on `links`, none starting with `INSERT`, `UPDATE` or `DELETE` (spec "The redirect performs no database write"). The counter call count is asserted through a counting decorator installed in the test container for that test. Alternative — assert through PostgreSQL statistics — rejected: shared with other tests and the dev stack.
9. **Logging and personal data** — every new log record carries ids and exception classes only: the recorder's `error` `{link_id, exception}`, the handler's `debug` `{click_id}` on a duplicate and `info` `{link_id, click_id}` on an orphan, the delete processor's `warning` `{link_id, exception}`. The IP and user agent are consumed by the hash in the request and never reach the queue, the worker or a log line (NFR-SEC-6, NFR-OBS-1).

## Applicability (high tier)

| Question | Applies? | Note |
|---|---|---|
| Crash before/after an external effect | yes | request: crash after the counter's `INCR` and before the dispatch → one counted click without a record, bounded to one per crash (stated in the spec, decision 1); crash after the dispatch → the message is on the stream, nothing lost. Worker: crash after the transaction's commit and before the ack → redelivery → duplicate primary key → acknowledged without a second increment (decision 4); crash before the commit → rollback, redelivery, one row |
| Concurrent writers | yes | N concurrent first redirects on an absent key: seed + compare + increment are one Lua script, executed atomically by Redis — exactly `max` allowed, the key seeded once (decision 2, ten-process test); a `PATCH` of `maxClicks` concurrent with redirects: each redirect evaluates the snapshot it loaded, so the requests in flight at the change complete under the old limit — bounded by the in-flight count, all persisted, corrected by the lift on the next redirect (decision 2, interleaving test through the seam in task 2.2); several workers on one consumer group: each message is delivered to one consumer, and the primary key protects against a redelivery to another (decision 4); `click_count` increments are `+ 1` in SQL, commutative |
| Money rounding | n/a | |
| Empty/zero/null inputs | yes | `max_clicks` null → no Redis at all (decision 1); persisted `click_count` 0 → seed 0; key absent or below the persisted count → lifted to it on the next call, so a link that becomes limited after an unlimited period, or a stale key after a failed cleanup, starts from the persisted count (decision 2); `click_count` already ≥ `max` → 410 before the counter; a limit raised while the key is at the old maximum → the next redirect is allowed; empty stream → the worker idles |
| Authorization boundary | n/a | no new endpoint; the redirect stays public; `messenger:failed:*` is an operator console command |
| Deletion/expiry | yes | link deleted with messages queued → FK violation caught outside the transaction → the handler returns, the worker acknowledges, `info`, never retried, never parked — proven through a real Worker (decisions 4, 7); the counter key is removed best-effort with the link (decision 6) and a stale key can never under-count because the script lifts it to the persisted count (decision 2); expiry is unchanged (checked before the counter) |
| Idempotency of retries | yes | the message's `click_id` is the primary key: a redelivery or `messenger:failed:retry` after a partial failure yields exactly one row and one increment (decision 4); the counter is not idempotent per message and does not need to be — it is incremented once per redirect, not per message |

## Risks / Trade-offs

- [The counter may overshoot after a key loss or a limit change] → seeded from the persisted `click_count`; the overshoot is bounded by the accepted increments not yet persisted at that moment (queued, dispatch-failed, parked, crashed before dispatch) plus the requests in flight at a limit change, and compounds with repeated loss — stated in the spec and FR-RED-3; AOF persistence in Compose; the analytics stage reports the exact count from `clicks`.
- [A limit change is not synchronised with in-flight redirects] → snapshot semantics stated in the spec (decision 2); the window is one request's duration; synchronising through Redis would add a hot-path dependency for every link and was rejected.
- [A counted click without a record after a crash between `INCR` and dispatch] → bounded to one per crash, stated; no compensation (a compensating `DECR` would itself be a second command on the hot path and could race).
- [`clickCount` lags the redirects] → FR-LNK-11 says eventually consistent; the specs and the how-to say so; tests consume the transport explicitly.
- [The worker is a new moving part: if nobody runs it, clicks accumulate in the stream] → `make worker` / the compose profile; `messenger:stats` in the how-to; Redis memory is the ceiling; the health endpoint already checks Redis.
- [Poison messages] → 3 retries then `failed`; `messenger:failed:show|retry` runbook in the how-to; a handler bug shows up as a parked message, not a lost click; proven by a Worker test that also fails when the failure transport is disabled.
- [The test retry delay differs from production] → only the `delay` differs (10 ms vs 1000 ms) and only under `when@test`; retries, multiplier and the failure transport are the same configuration, and the production values are asserted from `debug:config`.
- [Orphaned counter keys when Redis is down at deletion] → logged at `warning`; harmless (UUIDs are never reused); no TTL by design (a TTL would reset a live limit).
- [Deleting the synchronous recorder removes the baseline row 7 was meant to be measured against] → the measurement is a row-13 deliverable with documented commands on the final path; the baseline's numbers were never recorded.
- [The PHP serializer ties the stream to this codebase's class names] → one producer and one consumer in the same deploy; a rename would be a versioned change with a drained stream; stated as a non-goal.
- [Test suite shares the dev Redis] → counter keys are prefixed `test:` in the test environment and cleaned per test; the stream test uses a random stream name and `cleanup()`.

## Migration Plan

`make migration` (after `auto_setup: false` on `failed`) → review the generated class → `make migrate` → `make test-db`; rollback `doctrine:migrations:migrate prev` drops `messenger_messages` (no data worth keeping before the first failure). Deploy order: migration, code, then start the worker (`docker compose --profile worker up -d` / `make worker`); until the worker runs, redirects work and messages accumulate in the stream. Rollback of the code: the previous synchronous recorder returns; messages already in the stream would be consumed by no one — drain the stream with the new worker before rolling back, or accept the loss of those records.
