# Design — add-api-keys-and-rate-limiting

## Context

See `proposal.md` — Why. State: the `api` firewall (`config/packages/security.yaml`) is stateless, `pattern: ^/api(/|$)`, `provider: App\Auth\Security\UserProvider`, `user_checker: BlockedUserChecker`, `json_login` on `/api/v1/auth/token` with Lexik's handlers and `jwt: ~` as its only request authenticator and entry point; `access_control` grants `/api/v1/auth/`, the docs and `/api/v1` to `PUBLIC_ACCESS`, `/api/v1/admin/` to `ROLE_ADMIN`, the rest of `/api/` to `ROLE_USER`. `JwtProblemDetailsSubscriber` renders Lexik's events as problem details (401 for missing/invalid/expired tokens, 403 `blocked` for the user checker's `CustomUserMessageAccountStatusException`). Rate limiters live in `config/packages/framework.yaml`: `auth_ip` (10/min/IP, `AuthRateLimitSubscriber` at `kernel.request` priority 16, fail-closed), `redirect_ip` (60/min/IP, `App\Redirect\RedirectRateLimit`, fail-open with a `warning`), all `sliding_window` on `cache.rate_limiter` (Redis) with `lock_factory: lock.factory`; the test environment swaps `auth_ip`'s storage for an in-process `InMemoryStorage` (`services.yaml`, `when@test`) so one test client sees one window. Trusted proxies come from `TRUSTED_PROXIES` / `trusted_headers`; the two IP-keyed limiters have trusted-proxy tests (`tests/Api/Auth/RateLimitTest.php`, `tests/Web/Redirect/RedirectRateLimitTest.php`). `User` is a plain DataMapper entity with `Uuid` v7 ids; repositories are interfaces in `src/Auth/` with Doctrine implementations in `src/Auth/Repository/`; the schema is attribute-mapped from `src/` and every change is a migration under `migrations/`. `/health` is outside the firewall (`PUBLIC_ACCESS`, `HealthController` in `src/Shared/Health/`), refuses `?deep=1` in `prod` with a hand-built 404 problem body. `ProblemDetails::response()` (`src/Shared/Api/`) builds RFC 9457 bodies.

Verified in the installed Symfony (`vendor/symfony/security-http`, `security-bundle`): the `access_token` authenticator (`AccessTokenAuthenticator`, factory priority −40) takes a `token_handler` service implementing `AccessTokenHandlerInterface::getUserBadgeFrom(string): UserBadge` and `token_extractors` (services implementing `AccessTokenExtractorInterface`; `HeaderAccessTokenExtractor` matches the `Authorization` header with a regex); it builds a `PostAuthenticationToken` without copying badge attributes into the token; on failure it calls the configured `failure_handler` or answers an empty 401 with `WWW-Authenticate`. Lexik's authenticator (factory priority −10) `supports()` any request from which its `lexik_jwt_authentication.extractor.chain_extractor` extracts a token — any `Authorization: Bearer …` — and `AuthenticatorManager::executeAuthenticators` runs every supporting authenticator in priority order, stopping only when one returns a response: a failure response stops the chain, a stateless success (null) does not. So on one firewall a `Bearer lb_…` header would be claimed by Lexik first and fail with 401 before the access-token authenticator runs — unless Lexik's extractor declines it. Symfony's firewall also offers `request_matcher` for a header-based second firewall. `RateLimiterFactoryInterface::create(key)->consume()` returns a `RateLimit` with `isAccepted()`, `getLimit()`, `getRemainingTokens()`, `getRetryAfter()`. Inside the firewall listener (`kernel.request` priority 8) the authenticator listener runs before `security.access_listener` (`SecurityExtension`: listeners 546 → 565); `AuthenticatorManager::handleAuthenticationSuccess` dispatches `LoginSuccessEvent` (with `getPassport()`, `getRequest()`, `getFirewallName()`, `getAuthenticator()` and `setResponse()`) on every successful authentication — on a stateless firewall that is once per request — and a response set there is returned by the authenticator, which stops the chain before access control. The application's Doctrine connection (`config/packages/doctrine.yaml`) has no connect or statement timeout; `HealthProbe::databaseConnection()` builds its own PDO with `ATTR_TIMEOUT` 2 s and `statement_timeout=2000` for exactly that reason. CI creates the `app` database but migrates only `app_test` (`make test-db EXEC=`); the prod-kernel health tests run `SELECT 1` against `app`.

## Goals / Non-Goals

**Goals:** a second API credential that reuses everything the JWT path already has (provider, user checker, voters, access rules, problem-details errors) and adds exactly one new component per concern — a token handler, an extractor, a failure handler, one decorator to keep the JWT authenticator off `lb_` tokens; a key that is hashed at rest and shown once; a per-identity limit applied by one subscriber with one header writer; the production probe opened by an admin key without a second code path for key lookup; a reversible migration.
**Non-Goals:** see proposal. Design-level: no second firewall (rejected below); no custom authenticator class (the framework's `access_token` is the component for exactly this); no ORM write on the authentication path except the throttled `last_used_at` update; no cache of key lookups (one indexed `SELECT` per request is the cost of "revocation takes effect on the next request").

## Decisions

1. **One firewall, two authenticators; Lexik's extractor declines API keys.** `security.yaml`, firewall `api`, gains `access_token: { token_handler: App\Auth\ApiKey\ApiKeyTokenHandler, token_extractors: App\Auth\ApiKey\ApiKeyHeaderExtractor, failure_handler: App\Auth\ApiKey\ApiKeyAuthenticationFailureHandler }`; `jwt: ~` and `json_login` stay; `entry_point: jwt` stays (a request with no credential at all is still Lexik's 401). `ApiKeyHeaderExtractor` accepts only `^Bearer (lb_[A-Za-z0-9]{40})$` (the exact key shape — anything else is not a key and is left to Lexik). `App\Auth\ApiKey\JwtExtractorIgnoringApiKeys` decorates `lexik_jwt_authentication.extractor.chain_extractor` (`#[AsDecorator]`, the bundle's public extractor service, aliased to `TokenExtractorInterface`) and returns `false` when the extracted token starts with `lb_`, so Lexik's `supports()` is false for keys and the access-token authenticator (lower priority) handles them; a JWT never starts with `lb_` (three base64url segments of a JOSE header), so JWTs are untouched. Both sides are asserted: a unit test of the decorator, and HTTP tests that a key authenticates (Lexik did not claim it) and that a JWT still does. Alternatives — a second firewall `api_key` with a `request_matcher` on the `Authorization` header: also correct, rejected because it duplicates `provider`/`user_checker`/`stateless`/`access_control` reasoning for one header shape and splits the API's 401/403 rendering across two firewalls; a `custom_authenticators` class of our own: rejected — its priority (0) would run before Lexik but Lexik would still run afterwards on the same header and fail the request (Context), so the extractor decorator is needed anyway, and the framework's `access_token` authenticator is the right component once it is.
2. **Key format, generation, hashing.** `ApiKeyGenerator::generate(): GeneratedKey{plaintext, hash, prefix}`: `lb_` + 40 characters drawn from the 62-character alphabet with `random_int(0, 61)` per character (uniform, CSPRNG; ≈238 bits), `hash = hash('sha256', $plaintext)` (64 hex), `prefix = substr($plaintext, 0, 8)` (`lb_` + 5 characters — enough to tell keys apart in a list, useless to guess the key). Lookup by `key_hash` through a unique index; the plaintext exists only in the `POST` response DTO and is never logged (Monolog processors do not see DTOs; the processor never logs the input). Alternative — a password hasher (bcrypt) — rejected by the brief (FR-KEY-1 fixes SHA-256) and by the need for an indexed exact lookup: a 238-bit random key needs no slow hash.
3. **Entity, repository, migration.** `App\Auth\Entity\ApiKey` (`id` Uuid v7, `owner` ManyToOne `User` with `ON DELETE CASCADE`, `name`, `keyHash` char(64), `prefix` char(8), `expiresAt`, `revokedAt`, `lastUsedAt`, `createdAt`; methods `revoke(now)`, `isActive(now)` = not revoked and not expired, `touch(now)`), `ApiKeyRepositoryInterface` (`add`, `findById`, `findActiveByHash(hash, now)`, `listByOwner(owner, offset, limit)`, `countActiveByOwner(owner, now)`, `touchLastUsed(id, now, threshold)`), `DoctrineApiKeyRepository`. `touchLastUsed` is one DBAL statement — `UPDATE api_keys SET last_used_at = :now WHERE id = :id AND (last_used_at IS NULL OR last_used_at < :threshold)` with `threshold = now − 60 s` — so the once-per-minute rule is enforced atomically in the database and the authentication path never flushes the UnitOfWork. Migration `api_keys` per §3.2: PK, FK `user_id` → `users(id)` `ON DELETE CASCADE` with its index, `UNIQUE (key_hash)`, index `(user_id, created_at)` for the listing; `down()` drops the table. Alternative — a JSONB `api_keys` column on `users` — rejected: no unique index on the hash, no per-key rows for audit.
4. **Token handler and failure handler.** `ApiKeyTokenHandler::getUserBadgeFrom($accessToken)`: hash the presented value, `findActiveByHash` (not revoked, not expired, evaluated with the clock's `now`) or throw `BadCredentialsException` (rendered 401); on a hit, `touchLastUsed(id, now, now − 60 s)` and return `new UserBadge($user->getUserIdentifier(), fn () => $user, ['api_key_id' => (string) $key->getId()])` — the key id travels as a badge attribute, which the rate-limit listener reads from the passport of `LoginSuccessEvent` (decision 6); the authenticator does not copy it into the token (Context) and nothing else needs it. The firewall's `user_checker` then runs `BlockedUserChecker` for a blocked owner → `CustomUserMessageAccountStatusException('blocked')`. `ApiKeyAuthenticationFailureHandler::onAuthenticationFailure` maps `AccountStatusException` → `ProblemDetails::response(403, 'Forbidden', 'blocked')` and everything else → `ProblemDetails::response(401, 'Unauthorized', 'Invalid API key.')` — the same shapes `JwtProblemDetailsSubscriber` produces for JWTs. The handler never logs the presented value (`#[\SensitiveParameter]` on the parameter as the interface declares). Alternative — updating `last_used_at` through the entity and `flush()` — rejected: a UnitOfWork flush on every authenticated request, and a race between two requests of the same key.
5. **Resource `ApiKeys`** (`src/Auth/Api/ApiKeys/`): `ApiKeyOutput` DTO (`id`, `name`, `prefix`, `expiresAt`, `createdAt`, `lastUsedAt`, `revokedAt`) with `#[ApiResource(shortName: 'ApiKey')]` — `GetCollection /api-keys` (`provider: OwnApiKeysProvider`, paginated 30/100 like the links), `Post /api-keys` (`input: CreateApiKeyInput` — `name` `NotBlank` + `Length(max 64)` after trimming, `expiresAt` `?DateTimeImmutable` with `GreaterThan('now')`; `processor: CreateApiKeyProcessor`; `output: CreatedApiKeyOutput` = the same fields plus `key`; `status: 201`), `Delete /api-keys/{id}` (`provider: OwnApiKeyItemProvider` — loads the key by id **and owner**, 404 otherwise, so a foreign key is indistinguishable from an unknown one; `processor: RevokeApiKeyProcessor`, idempotent 204). All three `security: is_granted("ROLE_USER")`. The 10-key rule holds under concurrency (Gate 1 round 1, finding 1): `CreateApiKeyProcessor` runs count and insert in one database transaction that first locks the owner's row — `ApiKeyRepositoryInterface::lockOwner(User)` = `SELECT id FROM users WHERE id = :id FOR UPDATE` — so two creations for one owner serialise on that lock: the second waits for the first's commit, counts again under a fresh snapshot (`READ COMMITTED`: each statement sees rows committed before it starts), sees 10 and throws `ConflictHttpException` ("At most 10 active API keys per user."), which API Platform renders as 409 problem details with that `detail`; the transaction is rolled back and nothing is created. The lock is per owner, so unrelated users never wait on each other. Alternative — a Symfony `Lock` (Redis) around the processor — rejected: the database already serialises writers on a row and the invariant is a database fact; a Redis lock would add a second store to the write path. `ApiKeyVoter` (`API_KEY_VIEW`/`API_KEY_REVOKE`, owner only, no admin override) is added for the web UI to reuse and applied in `RevokeApiKeyProcessor` as a second check even though the provider already scoped by owner (defence in depth mirrors `LinkVoter`, and the web change will call the voter directly). Alternative — 422 for the 11th key — rejected: no field is wrong; the brief reserves 422 for validation.
6. **Per-identity limit at authentication time, before access control.** `framework.rate_limiter.api_identity`: `sliding_window`, `limit: '%env(int:RATE_LIMIT_API_PER_KEY)%'`, `interval: '1 minute'`, `cache_pool: cache.rate_limiter`, `lock_factory: lock.factory`; `.env`: `RATE_LIMIT_API_PER_KEY=600`; `when@test` switches its storage to the in-process `app.rate_limiter.test_storage` like `auth_ip` (one window per test client). `App\Auth\RateLimit\ApiRateLimitListener` listens to `LoginSuccessEvent` (Gate 1 round 1, finding 2 — a `kernel.request` listener at priority 7 would run after the whole firewall, including the access listener's 403, so role-denied requests would never be counted): it acts when `getFirewallName()` is `api`, the request is the main request and its path does not match `^/api/v1/auth/` (the `json_login` success on `/api/v1/auth/token` is not API traffic); the identity key is `key:<api_key_id>` from the passport's `UserBadge` attributes (decision 4) or `user:<user id>` for a JWT; `create(key)->consume()` inside `try/catch (\Throwable)` → on a store failure log `warning` `{exception class}` and return (fail-open, no headers — the same posture as `RedirectRateLimit`); when accepted, stash the `RateLimit` in a request attribute; when rejected, `$event->setResponse(ProblemDetails::response(429, …))` with `Retry-After`, `X-RateLimit-Limit`, `X-RateLimit-Remaining: 0` — the authenticator returns that response and the chain stops, so neither the access listener nor any operation runs. Because the event fires inside the authentication of every stateless request, consumption is exactly once per main request, for both credentials, and it precedes access control: a user's key hammering `/api/v1/admin/…` is counted on every 403 and reaches 429. `kernel.response` (`ApiRateLimitHeaders`): when the request carries a stashed `RateLimit`, add `X-RateLimit-Limit` and `X-RateLimit-Remaining` — on 2xx, on the access listener's 403, on 404/422 alike. Unauthenticated requests never authenticate, so they are never limited or decorated; the docs and `/api/v1` are public and unlimited. Alternative — `kernel.request` after the firewall — rejected for the reason above; a request listener *before* the firewall — rejected: there is no identity yet; an API Platform provider — rejected: it would not cover every operation uniformly and runs after deserialization.

7. **Deep probe with an admin key — bounded lookup, fail-closed.** `App\Auth\ApiKey\ProbeKeyResolver::resolveAdmin(?string $authorizationHeader): bool` is built like `HealthProbe` (Gate 1 round 1, finding 3): it does not use the application's Doctrine connection (no timeouts) but its own PDO from `DATABASE_URL` with `ATTR_TIMEOUT` 2 s and `statement_timeout=2000` — the probe's `databaseConnection()` factored into a shared `BoundedDatabaseConnection` helper — and runs one statement, `SELECT u.roles, u.is_blocked, k.expires_at, k.revoked_at FROM api_keys k JOIN users u ON u.id = k.user_id WHERE k.key_hash = :hash`, after matching the header with the extractor's regex and hashing the value. It answers true only for a row that is not revoked, not expired (the clock's `now`), of an unblocked user whose `roles` contain `ROLE_ADMIN`; false otherwise; and false — fail-closed — on any `\PDOException`, timeout or malformed URL, with a `warning` "deep probe authorization unavailable" naming the failure class so an operator can tell a database failure from an invalid key in the logs while the client cannot (the response is the same 404). It never writes `last_used_at`. `HealthController`, in `prod`, runs the probe when `resolveAdmin()` is true, else the existing 404. Budget: the lookup takes at most about 2 s to connect plus 2 s per statement before the 404; when the database is down or stalled the probe is not executed and the monitor receives a 404 within that budget — a monitor must alert on any non-200 from the deep probe, not only on 503 (Risks; the how-to says so). `/health` stays outside the firewall (spec "outside the API contour"). Alternative — the application repository through Doctrine — rejected: unbounded, and the resolver would hang exactly when the probe is needed; moving `/health` under the firewall — rejected: it would require authentication for the liveness probe too; caching key hashes in Redis to authorize while the database is down — rejected: a second authorization store for a monitor's convenience.

8. **Tests.** *Unit*: `ApiKeyGenerator` (shape regex, 200 distinct keys, hash = sha256, prefix = first 8), `JwtExtractorIgnoringApiKeys` (`Bearer lb_…` → false, a JWT-looking token → passed through), `ApiKeyHeaderExtractor` (regex accepts the shape, rejects `Bearer eyJ…`, `lb_` of wrong length, lowercase `bearer`), `ApiKeyVoter` (owner true, stranger false, admin-stranger false), `ApiKey::isActive` (revoked, expired, both null). *Integration*: `DoctrineApiKeyRepository` — `findActiveByHash` ignores revoked/expired, `touchLastUsed` writes once per minute (two calls, second no-op), `countActiveByOwner`, cascade on user deletion; the migration applies and reverts (`doctrine:migrations:migrate prev` in the test DB); `ApiKeyCreationConcurrencyTest` — from nine active keys, 12 processes create concurrently (`tests/Fixture/create-api-key.php`, committed rows in `app_test`, cleaned up after): exactly one succeeds, the rest get the conflict, ten active keys remain. *Api*: `ApiKeysTest` — plaintext once + hashed at rest (`SELECT key_hash`), 422 matrix, 11th key 409 then 201 after a revoke, own-keys listing, revoke twice/foreign/admin-foreign 404; `ApiKeyAuthTest` — key works on `/me`, `lastUsedAt` set then unchanged within the minute, revoked/expired/unknown/malformed 401 problem+json, blocked 403 `blocked`, unblock restores, JWT still works, stranger with a key gets 403 on a foreign link (voters); `ApiRateLimitTest` — headers 600/599, exhaustion → 429 with `Retry-After` and no operation executed (a `POST /links` over the limit creates nothing), separate windows per key/user, role-denied requests are counted (an ordinary user's key and JWT on `GET /api/v1/admin/stats/summary`: 403 with the headers each time, then 429), `/api/v1/auth/token` and anonymous requests carry no headers, store unavailable → 200 without headers + `warning` (the `api_identity` limiter swapped for a factory whose storage throws, through the test container); `HealthDeepProdTest` — with the `APP_ENV=prod` kernel and the admin/key rows inserted into the `app` database through the bounded connection (committed, removed in `finally`; CI migrates `app` for this — decision 10): no header 404, JWT 404, non-admin key 404, revoked admin key 404, blocked admin's key 404, admin key → probe body; `ProbeKeyResolverTest` (integration): an unreachable `DATABASE_URL` → false within 3 s with a `warning`, `SELECT pg_sleep(10)` on the resolver's connection is cancelled by the statement timeout (as `HealthProbeTest` does for the probe), a missing `api_keys` table → false, not an exception. Failing inputs per guard, recorded in the commit bodies: dropping the `revoked_at IS NULL` predicate from `findActiveByHash` makes the revoked case 200; dropping the threshold from `touchLastUsed` fails the once-per-minute case; removing the decorator makes the key request 401 (Lexik claims it); removing the `isAdmin()` check makes the non-admin probe case pass; removing the `try/catch` fails the store-unavailable case with 500; removing the `X-RateLimit-Remaining` header fails the header case; removing the owner scope from `OwnApiKeyItemProvider` makes the foreign `DELETE` 204; moving the limiter to a `kernel.request` listener at priority 7 fails the role-denied case (403 without headers, never 429); removing the resolver's `try/catch` turns the unreachable-database case into a 500; removing `lockOwner()` lets the concurrency test produce more than ten keys (the race is real, its outcome per run is not deterministic — recorded like the limiter's `--no-lock` input).
9. **Logging and personal data.** New records: `warning` `{exception}` when the API limiter's store is unavailable. Nothing logs a key, its hash or its prefix; the 401 detail is constant (`Invalid API key.`) whatever the reason, so an attacker cannot tell unknown from revoked from expired. `last_used_at` is the only per-request write and carries no IP.
10. **CI migrates the `app` database too.** `.github/workflows` gains `make migrate EXEC=` before `make test-db EXEC=`, so the prod-kernel tests (which read `DATABASE_URL` without the `_test` suffix) find the `api_keys` schema in `app` exactly as a deployed instance would after `make migrate`. Locally `make init` already migrates it. Alternative — pointing the prod kernel at `app_test` in tests — rejected: the health tests deliberately probe the configured dependency as is.

## Applicability (high tier)

| Question | Applies? | Note |
|---|---|---|
| Crash before/after an external effect | yes | Creation is one transaction (owner lock, count, insert) — a crash before the commit leaves nothing, after it the key exists and its plaintext was in a response the client may not have received; the client sees no `key` in the list either way and creates another (10-key cap). Revocation is one `UPDATE`. `touchLastUsed` is one statement outside any transaction — a crash after it leaves a truthful timestamp. The limiter's `consume()` is a Redis read-modify-write under the shared lock; a crash after it costs one token. |
| Concurrent writers | yes | Two creations at nine active keys serialise on the owner's row lock inside one transaction (decision 5): one commits the tenth, the other recounts and gets 409 — asserted by the concurrency test with 12 processes. Two requests with one key at the same second: `touchLastUsed` is a single conditional `UPDATE`, both see a consistent row; the limiter's sliding window is protected by `lock.factory` like the other limiters. Revoke twice concurrently: both `UPDATE … SET revoked_at = coalesce(revoked_at, :now)`-equivalent through the entity (`revoke()` is a no-op when already revoked), both 204. |
| Money rounding | n/a | — |
| Empty/zero/null inputs | yes | `name` empty or blank → 422 on `name`; `expiresAt` absent → never expires, past → 422 on `expiresAt`; `Authorization: Bearer lb_` (nothing after) or wrong length → not matched by the extractor → Lexik's 401 (malformed token) — still 401 problem details; `RATE_LIMIT_API_PER_KEY=0` is a misconfiguration the limiter rejects at boot (Symfony requires a positive limit) — documented; an empty listing → `items: []`. |
| Authorization boundary | yes | Keys: the item provider loads by id **and** owner (404 for a foreign key — no oracle), `ApiKeyVoter` owner-only with no admin override (matrix "own / own"), collection scoped by owner; asserted over HTTP for owner/stranger/admin. Authentication: hash lookup + active check + `BlockedUserChecker` on the same firewall (403 `blocked`), constant 401 detail; JWTs untouched (decorator only declines `lb_`). Probe: the `prod` branch requires the bounded resolver to return true (unrevoked, unexpired key of an unblocked admin); every refusal — including a database that is down or stalled — is the same 404 within the timeout budget, so the probe is neither an oracle for keys nor an unbounded call. Failing inputs in decision 8. |
| Deletion/expiry | yes | Revocation keeps the row (audit) and stops the key on the next request; `expires_at` is evaluated at every lookup with the clock; a deleted user cascades their keys (FK); a revoked or expired key still appears in the owner's list with its timestamps. |
| Idempotency of retries | yes | `DELETE /api-keys/{id}` twice → 204 twice; `POST /api-keys` twice → two keys (no idempotency key — the cap bounds the damage, and the cap holds under concurrency); a retried authenticated request consumes another limiter token (the point of the limit). |

## Risks / Trade-offs

- [The owner-row lock serialises a user's own key creations] → only that user's concurrent creations wait, for the duration of one count and one insert; nothing else locks `users` rows.
- [Deep probe in `prod` answers 404 while the database is down, because the key cannot be verified] → the monitor must alert on any non-200 from `?deep=1`, not only on 503 (how-to); liveness `/health` stays independent of every store; the `warning` names the failure class for operators.
- [A lost `POST` response loses the plaintext forever] → by design (plaintext once); the how-to says so and shows revoking and re-creating.
- [`last_used_at` costs one `UPDATE` per key per minute] → bounded by the once-a-minute predicate evaluated in the database; no ORM flush; the read path of the API is otherwise unchanged.
- [Fail-open limiter] → a Redis outage removes the API limit but never the API; the `warning` is the alarm; the same posture the redirect limiter established, and a monitor holding an admin key sees `redis: fail` in the deep probe (the key is verified against the database, not Redis).
- [Decorating a bundle service id] → `lexik_jwt_authentication.extractor.chain_extractor` is the id the bundle itself aliases to `TokenExtractorInterface` and injects into its authenticator; a bundle upgrade renaming it fails at container compile time (the decorated service would be missing), not silently — and the HTTP test "a key authenticates" would catch a silent behaviour change.
- [`access_control` is path-based, both credentials share it] → intended: FR-AUTH-3 says both resolve to the same rules; nothing key-specific is granted.
- [Key in `Authorization` header of a monitor hitting `/health`] → the header travels over TLS like a JWT would; the probe never echoes it, never logs it, and refuses with the same 404 whatever the reason.
- [`api_identity` uses the Redis pool in `dev`/`prod`, in-memory in `test`] → the same split `auth_ip` already lives with; the Redis path of the storage is covered by the existing `RateLimiterStorageTest` pattern (a Redis-backed sibling limiter consumed in an integration test) — reused for `api_identity` in task 3.1.

## Migration Plan

Deploy: `make migrate` creates `api_keys`; the new firewall entry and limiter are configuration; `RATE_LIMIT_API_PER_KEY` has a default in `.env`. Rollback: revert the code and configuration, then `doctrine:migrations:migrate prev` drops the table (revocable — keys are re-creatable credentials). No data migration.
