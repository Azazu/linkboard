# Design — add-web-ui

## Context

See `proposal.md` — Why. What exists today, verified in the tree: `src/Web/` holds three controllers (`HomeController`, `LoginController` with `/logout`, `RegistrationController` with `RegistrationFormType` over the API's `RegistrationInput`), and `templates/` holds the Symfony skeleton's `base.html.twig` — no viewport, no navigation, no flash region, and two `cdn.jsdelivr.net` script tags behind a `FRANKENPHP_HOT_RELOAD` guard this deployment never sets. There is no `assets/`, no `importmap.php`, no AssetMapper and no UX bundle; `symfony/form`, `symfony/validator`, `symfony/twig-bundle` and (transitively) `symfony/security-csrf` are installed. CSRF is stateless with the token ids `submit`, `authenticate`, `logout` (`config/packages/csrf.yaml`), so a Symfony form needs nothing extra and a hand-written form needs `csrf_token('submit')`. `framework.yaml` has a bare `session: true` — no cookie flags. **No response header is set anywhere** except the redirect's `Referrer-Policy` and a few `Cache-Control: no-store`: NFR-SEC-5 is unimplemented.

What the pages can build on: `LinkRepositoryInterface` (`findPageForOwner`, `countForOwner`) with `LinkListQuery` (active state, slug fragment, order by `createdAt|clickCount`); `LinkVoter` with `LINK_VIEW|LINK_EDIT|LINK_DELETE` — **voting on `LinkResource`, not on the entity**, so a controller must convert through `PublicUrl::toResource()` first, exactly as `LinkReportProvider` does; `ApiKeyVoter` (`API_KEY_VIEW|API_KEY_REVOKE`, owner only, no admin override); `QrCodeRenderer` and `QrFormat`; `RulesDocumentParser::parse()` returning violations with a path rather than throwing; `TargetUrlPolicy`; `CreateApiKeyProcessor::create(User, CreateApiKeyInput)`, already public for exactly this reason. `ReservedSlugs::LIST` already reserves `dashboard`, `links`, `api-keys` and `assets`, and `ReservedSlugsCoverRoutesTest` checks that against the live router.

What it cannot build on, and why this change moves it: the link write path lives inside API Platform processors that read the **raw JSON request body** — `CreateLinkProcessor` takes the rules through `RulesInput::fromRequest($context['request'])`, `UpdateLinkProcessor` derives its merge-patch presence map from the same body — and throws `ApiPlatform\Validator\Exception\ValidationException`. A form post has no such body. The analytics layer has the matching gap: `LinkSummaryQuery` is per link, `GlobalStatsQuery` is instance-wide, and `Sql::link()` scopes only by `link_id`; nothing answers "this owner's clicks".

## Goals / Non-Goals

**Goals:** pages whose authorization is the API's, expressed once; one authority for every link write; a content security policy that is enforceable rather than aspirational, with the asset pipeline arranged so the policy needs no `unsafe-inline`; a suite that proves the owner/stranger/guest matrix on every page and the headers on a rendered one.
**Non-Goals:** see proposal. Design-level: no new authenticator, firewall or user-facing role; no change to the API's routes, payloads or status codes; no second validation vocabulary — the pages report the constraints the API already declares; no client-side state beyond the three Stimulus controllers named below; no server-side rendering of the chart.

## Decisions

1. **Controllers by feature under `src/Web/`, one page each.** `src/Web/Dashboard/DashboardController`, `src/Web/Link/{LinkListController,LinkCreateController,LinkShowController,LinkEditController,LinkDeleteController,LinkQrController}`, `src/Web/ApiKey/{ApiKeyListController,ApiKeyCreateController,ApiKeyRevokeController}`, each `final` and invokable, extending `AbstractController` like the existing three. Templates mirror them: `templates/dashboard/`, `templates/link/`, `templates/api_key/`. Alternative — one fat controller per feature — rejected: the authorization check would be shared by paths with different subjects, which is how a page ends up unprotected.
2. **One authority for link writes: `src/Link/UseCase/`.** `CreateLink::__invoke(User $owner, NewLink $data): Link` owns the slug loop (generate, pre-check, `MAX_ATTEMPTS`, manager reset after a unique violation) and throws `SlugTaken` when a *client-supplied* slug loses the race. `UpdateLink::__invoke(Link $link, LinkChanges $changes, ?User $actor): void` applies the changes, flushes, invalidates the link's cached reports and writes the admin audit line. `DeleteLink::__invoke(Link $link, ?User $actor): void` removes, flushes, forgets the click counter and both cache scopes, and audits. `NewLink` and `LinkChanges` are readonly value objects; `LinkChanges` carries, per field, *leave it* or *set it to this (null clears)* — an explicit `Change` wrapper rather than "null means absent", because null is a legal new value for expiry, click limit, UTM and rules. The three API processors become adapters: they build the value objects from the JSON body (keeping `RulesInput` and the presence map, which are HTTP concerns), translate `SlugTaken` into the 422 `ValidationException` the API already returns, and render `LinkResource`. The web controllers build the same value objects from a form, and translate `SlugTaken` into a form error on the slug field. Alternatives rejected: calling the processors from the web (they need a JSON body and an API Platform `Operation`); duplicating the orchestration in `src/Web/` (two copies of ownership, slug and cache-invalidation logic — the defect class AGENTS.md names as this workflow's most expensive).
3. **Authorization is asked per page, on the voter's own subject.** Every link page loads the entity, converts it with `PublicUrl::toResource()` and asks `LinkVoter::VIEW|EDIT|DELETE`; a denial and an unknown identifier both produce **404**, never 403, so a signed-in stranger learns nothing from the page. This differs from the API on purpose, and the artifacts of round 1 wrongly claimed otherwise (Gate 1 round 1, finding 4): the `links` and `qr-codes` capabilities require **403** for a stranger's API call — a machine contract where a client benefits from knowing its credentials were accepted and the object is somebody else's — and that contract does not change here. A rendered page has no such consumer, so it discloses less. One authorization decision (the voter), two renderings, each stated where it belongs. Guests never reach a controller: `security.access_control` refuses `^/(dashboard|links|api-keys)(/|$)` to anonymous users, and the firewall's entry point sends them to `/login`. **The `(/|$)` is not decoration** (Gate 1 round 1, finding 1): an access-control pattern is an unanchored regular expression over the path, `ReservedSlugs` reserves exact strings only, and `dashboard-sale`, `links-promo` and `api-keys-promo` are all valid slugs — without the boundary those public short links would be sent to the login page, breaking the `redirect` capability's anonymous redirect. The same boundary idiom is already in the file, on the `api` firewall's own pattern, for the same reason. The list and the dashboard never rely on a voter at all: their SQL is scoped by `owner_id`, so a row that is not the user's cannot be rendered even if a check were forgotten. Alternative — `#[IsGranted]` on the controller — kept for the role check only; the object check needs the converted resource.
4. **The dashboard's figures come from one owner-scoped query, uncached.** `src/Analytics/Query/OwnerDashboardQuery` adds `totals(Uuid $ownerId, \DateTimeImmutable $startOfToday): OwnerTotals` (links, active links, clicks, unique visitors, clicks today) and `daily(Uuid $ownerId, Period $period): array` (`list<ClickBucket>` over the owner's links, zero-filled by `generate_series` like the existing timeseries, bots excluded through `Sql::bots()`), both joining `clicks` to `links` on `links.owner_id = :owner`. It is **not** put behind `ReportCache`: the report cache is invalidated by link tag, and a dashboard keyed by owner would go stale for five minutes after a link is created or deleted through the API — an invalidation hole across two layers, in exchange for saving two index-backed statements on a page one person opens. The cost is stated rather than hidden: if the figures ever become expensive, the fix is an owner tag on the cache *and* invalidation in the same use cases of decision 2, which is the point of having them. The plan of both statements is checked with `EXPLAIN`; a new index ships as a migration only if the plan asks for one.
5. **Assets: AssetMapper with an import map, no Node, no CDN.** `importmap.php` pins Turbo, Stimulus and Chart.js as vendored files under `assets/vendor/` (`importmap:require` downloads them once, at development time, and they are committed); Pico.css arrives the same way as a CSS asset. `assets/app.js` starts Stimulus and Turbo; `assets/controllers/` holds exactly three controllers — `clipboard` (the copy button), `rules-editor` (add and remove a rule row, toggle the raw-JSON view) and the chart controller the chart bundle ships. The import map's polyfill is **switched off**: it is an inline loader whose nonce cannot be baked in, and every browser this project targets supports import maps natively. Alternative — a Node build (Webpack Encore/Vite) — rejected by FR-WEB-3 and by the anti-overengineering rule.
6. **A content security policy with a per-request nonce, and one subscriber that sets it.** `src/Web/Http/CspNonceListener` (on `kernel.request`) puts 16 random bytes, base64-encoded, on the request attributes; a Twig function `csp_nonce()` reads them, and the layout passes the value to `importmap()`, which applies it to the import-map script and the entry-point module (verified against `symfony/asset-mapper`'s `ImportMapRenderer`: both `render()` and the bundle's `script_attributes` accept a nonce, and the polyfill — switched off in decision 5 — is the only tag that deliberately drops one). `src/Web/Http/SecurityHeadersSubscriber` (on `kernel.response`) then sets `X-Content-Type-Options: nosniff` on **every** response, and on HTML responses `X-Frame-Options: DENY`, `Referrer-Policy: strict-origin-when-cross-origin` and `Content-Security-Policy: default-src 'self'; script-src 'self' 'nonce-…'; style-src 'self'; img-src 'self' data:; font-src 'self'; connect-src 'self'; frame-ancestors 'none'; base-uri 'self'; form-action 'self'; object-src 'none'`. `img-src` admits `data:` because the QR code is rendered inline as a data URI on the link page; `style-src` stays `'self'` — Chart.js sizes its canvas through the CSSOM, which a policy does not restrict, and the layout carries no style attribute. **Not covered:** the API documentation page. API Platform's Swagger UI bootstraps with an inline script of its own; rather than admit `unsafe-inline` for everybody or pretend a nonce reaches a third-party template, the policy is not sent under `^/api(/|$)` — the boundary again, because `^/api` alone would also exempt `/api-keys`, the one page of this change that renders a secret (Gate 1 round 1, finding 2). Excluded responses keep all three of the other headers — `nosniff`, `X-Frame-Options: DENY` and the referrer policy — and lose only the content security policy; the API's JSON responses carry `nosniff` and nothing else, since the remaining headers govern documents a browser renders. The exemption is one page, named in the spec and in the how-to. Alternative — hashes instead of a nonce — rejected: the import map's content changes with every asset version, so the hash would have to be recomputed at build time and would silently break on a stale one.
7. **Session cookies are hardened in configuration, not in code:** `framework.session` gains `cookie_httponly: true`, `cookie_samesite: lax` and `cookie_secure: auto` (`auto` is `Secure` whenever the request is HTTPS, which is what a local plain-HTTP stack needs and what production gets behind TLS). `SameSite=Lax` keeps the login redirect working; `strict` would break the post-login navigation from an external link.
8. **Forms are Symfony forms over the API's input DTOs where they exist.** Registration keeps `RegistrationInput`. Link creation and editing get `src/Web/Link/{LinkType,RulesType}` bound to new form DTOs in `src/Web/Link/` — not to `CreateLinkInput`/`UpdateLinkInput`, whose `#[ValidRules]` constraint reads the raw HTTP body and would always see nothing in a form post. The form DTOs carry the same `Assert` constraints plus the project's `Slug` and `TargetUrl` constraints, so the violations are the API's; the rules document is validated by `RulesDocumentParser` and its `RuleViolation::$path` is mapped onto the form's error paths. A small Twig form theme renders Pico-shaped markup and gives every error `role="alert"` — the selector the existing web tests already use.
9. **Turbo's contract with the server:** a successful form post answers `303` to the page that shows the result; an invalid one re-renders with `422`, which is what Turbo needs to replace the form and what `RegistrationController` already does. Deletion is a POST with a confirmation step, never a GET — a link in an e-mail must not delete anything.
9a. **What "shown once" guarantees, and what it only mitigates** (Gate 1 round 1 finding 3, and its first confirmation). The **guarantee is server-side**: the plaintext exists in exactly one response and the server cannot produce it again — only the SHA-256 is stored, which is the `api-keys` capability's own rule. Everything else is mitigation of client-side retention, and the artifacts now say so rather than promising a browser will comply:
    - `data-turbo-temporary` on the element that holds the secret — Turbo Drive removes it from the snapshot it takes just before navigating away, so a Turbo restoration paints the page without it;
    - `<meta name="turbo-cache-control" content="no-cache">` on that page — Turbo does not cache it at all and refetches on a restoration visit;
    - `Cache-Control: no-store` on the response — for HTTP caches and proxies. It is **not** a back-forward-cache exclusion: Chrome keeps `no-store` documents in the back-forward cache under documented conditions, so the earlier draft's claim that this header covered "any cache the browser keeps" was wrong;
    - a `pageshow` handler in the Stimulus controller that owns the secret element: when the browser restores the document from its history (`event.persisted`), the element is emptied. This is the only mechanism that acts on a document the browser restores by itself — and it needs JavaScript, which is why it is a mitigation and not the guarantee.
    **Not guaranteed, and stated in the spec and the how-to:** a browser that restores its own rendered document with scripting disabled, a screenshot, or the user's clipboard. No test claims otherwise.
    **Measured, not assumed:** the acceptance run of task 4.9 drives the real page in headless Chromium — a Turbo navigation away and back, and a full-document navigation away and back — and records what the browser actually did. Its negative half needs care, because the mitigations overlap and the first draft's did not actually fail (confirmation 2 of round 1): each protection has to be removed against the restoration it governs, on a **fresh** secret-bearing page, with the HTTP `no-store` header kept throughout.
    - *Turbo restoration*: `data-turbo-temporary` **and** `<meta name="turbo-cache-control" content="no-cache">` both removed. Removing only the first proves nothing — a `no-cache` page is fetched over the network on a restoration visit, so Turbo would show the consumed flash whatever the snapshot held.
    - *Full-document restoration*: only the `pageshow` clearing removed; the Turbo markings are irrelevant to a navigation the browser performs itself. The run must also record **whether a persisted restoration actually happened** — `pageshow` with `event.persisted`, or the absence of a network request for that URL on the way back. A browser that refetches has not exercised the guard, and the run says so instead of reporting a pass: an unexercised case is recorded as unexercised.
    The tooling was verified before the task was written (Chromium 152 driven by `puppeteer-core` from a directory outside the repository, so no Node toolchain enters the project, which FR-WEB-3 forbids); it is a local acceptance step, not part of `make check`, because CI has no browser.

10. **Tests.** *Web* (`tests/Web/`): for every page, the owner sees it, a stranger gets 404 (link pages) or sees only their own rows (list, dashboard, keys), and a guest is redirected to `/login`; the create, edit and delete flows end in the state the API reports; an invalid target, a taken slug, a bad rules document and a missing CSRF token each leave the store untouched and re-render 422; the key plaintext appears once; the dashboard's numbers count only the signed-in owner's links; a rendered page carries the four headers, a policy naming no foreign origin, and a nonce that differs between two responses and matches the inline script's. *Integration*: `OwnerDashboardQuery` against real PostgreSQL — two owners, bots excluded, zero-filled days, the period boundaries; `EXPLAIN` on both statements recorded in the task. *Unit*: `LinkChanges` (leave vs set-to-null), and the mapping from `RuleViolation::$path` to a form error path. *Api* (unchanged files): the existing `tests/Api/Link` suite is the net under decision 2's refactor and must stay green without edits. **Failing inputs to demonstrate:** the voter call removed from the show/edit/delete controller → the stranger case returns 200; the `owner_id` predicate dropped from the list query → another owner's link appears; the CSRF token id changed → the missing-token case succeeds; `X-Frame-Options` or the policy removed → the header test fails; the nonce made constant → the two-response test fails; `SlugTaken` swallowed → the taken-slug case creates a second link or 500s; the rules parser's violations ignored → the invalid document is stored; **the `(/|$)` dropped from the access-control pattern → the prefix-slug redirect test sends `/dashboard-sale` to the login page; the policy's exclusion widened back to `^/api` → the `/api-keys` header test fails; any one of `data-turbo-temporary`, the cache-control meta and the `pageshow` clearing removed from the new-key page → the markup test fails; and in the browser, the two negative cases of task 4.9 — both Turbo markings removed for the Turbo restoration, the `pageshow` clearing removed for a persisted full-document restoration — observe the plaintext coming back, each on a fresh key, which is the demonstration markup cannot make.**
11. **The skeleton's CDN tags go.** `base.html.twig` is rewritten around the shell; the FrankenPHP hot-reload block is deleted rather than kept behind a guard, because a policy that has to allow `cdn.jsdelivr.net` for a feature this deployment cannot use is worse than no feature.

## Applicability (high tier)

| Question | Applies? | Note |
|---|---|---|
| Crash before/after an external effect | yes | The external effects are the database flush, the report-cache invalidation and the audit line. `UpdateLink`/`DeleteLink` flush first, then invalidate (best effort, already the processors' order) and then audit, so a crash can leave a stale cached report for at most its 300-second lifetime and can lose an audit line for a write that happened — the same admitted behaviour the API has today, now in one place instead of two. |
| Concurrent writers | yes | Two creations can pick the same generated slug: the unique index decides and `CreateLink` retries after resetting the manager (`MAX_ATTEMPTS`), unchanged from the processor. A custom slug that loses the race raises `SlugTaken`, which the UI renders as a field error. API-key creation keeps the owner-row lock and the cap inside `CreateApiKeyProcessor::create()`. Two editors of one link are last-writer-wins on a field basis, as the API is; the page shows the stored state after the write. |
| Money rounding | n/a | — |
| Empty/zero/null inputs | yes | An emptied expiry, click limit, UTM or rules field means *clear it* and is expressed as `Change::to(null)`; a field the form does not carry is *leave it*. An empty rules textarea clears the document; whitespace-only input is treated as empty rather than as invalid JSON. A zero or negative click limit is refused by the same constraint the API uses. An empty filter or an out-of-range page number on the list is the unfiltered first page, not an error. |
| Authorization boundary | yes | Three layers, each stated where it is enforced: `access_control` keeps guests out of `^/(dashboard|links|api-keys)(/|$)` — the boundary keeps public short links such as `/dashboard-sale` out of the rule; every link page asks `LinkVoter` on the converted `LinkResource` and answers 404 on denial; every list query is scoped by `owner_id` in SQL. API keys are owner-only (`ApiKeyVoter`, no admin override) both to list and to revoke. Administrators reach another user's link pages, and their writes produce the audit line `UpdateLink`/`DeleteLink` emit. Failing inputs for each in decision 10. |
| Deletion/expiry | yes | Deletion is a confirmed, CSRF-protected POST; it cascades the link's clicks as the schema already does, forgets the click counter and both cache scopes, and leaves the page 404 afterwards. An expired or click-limited link still renders for its owner — expiry governs the redirect, not the pages — and is shown as such. |
| Idempotency of retries | yes | Every page is a `GET` with no effect. A re-submitted creation creates a second link (there is no idempotency key in this project and none is invented); a re-submitted revocation is the API's idempotent conditional update; a re-submitted deletion of an already deleted link is 404. Turbo's `303` after a write keeps the browser from re-posting on reload. |

## Risks / Trade-offs

- [Four new production dependencies] → each is named by the brief §2.9 and justified in the proposal; all four are Symfony-maintained, and the pipeline they replace (a Node toolchain) is the thing FR-WEB-3 forbids. If `symfony/ux-chartjs` turns out not to support Symfony 8.1 at implementation time, the fallback is a local Stimulus controller over the same self-hosted Chart.js from the import map — the chart stays, one dependency drops, and the task says so.
- [The dashboard is uncached] → decision 4 states the trade-off and the migration path; the `EXPLAIN` task is what keeps it honest.
- [The policy is asserted at the header and markup level, not in a browser] → a `WebTestCase` can prove the header and the absence of foreign origins in the markup, not that a real browser runs the page without violations; the browser-observable half of the secret's handling is covered by the acceptance run of task 4.9 instead, whose result is recorded rather than assumed, and the policy's own browser behaviour stays a stated gap. The screenshot task of row 13 and the manual check recorded in the how-to cover the rest; no test claims more than it checks.
- [`/api/docs` is outside the policy] → decision 6; the page carries the other headers, is unauthenticated by design, and serving Swagger UI under a nonce would mean patching a third-party template.
- [The write-path refactor touches code the API's tests cover but the UI's do not yet] → the refactor lands in its own commit with the API suite green before any page is written, so a regression is attributable.
- [Turbo changes navigation behaviour] → progressive enhancement only: every page is a full server render, and the no-JavaScript scenario in the spec is a test, not a claim.

## Migration Plan

No schema change unless `EXPLAIN` asks for an index (a reviewed migration then). Deployment needs `composer install` for the four new packages and the asset pipeline's one-time command (`assets:install` already runs in `auto-scripts`; the vendored import-map files are committed, so no network access is needed at deploy time). Rollback is removing the routes and the subscriber; nothing in the database changes shape.
