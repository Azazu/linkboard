# Design — authorize-deep-probe-by-api-key

## Context

See `proposal.md` — Why. State: `HealthController` (`src/Shared/Health/`) answers `GET /health` (liveness) and `GET /health?deep=1` through `HealthProbe`, which deliberately builds its own raw clients from `DATABASE_URL` / `REDIS_URL` rather than the application's Doctrine connection or cache pool: a PDO with `ATTR_TIMEOUT` 2 s (mapped by pdo_pgsql to libpq's `connect_timeout`) and `options='-c statement_timeout=2000'`, and an ext-redis client with 2-second connect and read timeouts — so a down or hung dependency fails the check instead of hanging it; `HealthProbeTest` proves both bounds. In `prod` the controller returns a hand-built 404 problem body with `Cache-Control: no-store` for `?deep=1`. `/health` is `PUBLIC_ACCESS` in `access_control` and outside every firewall and the OpenAPI document. The archived change `add-api-keys-and-rate-limiting` left in `main`: `api_keys` (`key_hash` char(64) unique, `expires_at`, `revoked_at`, `user_id` → `users` with `roles` jsonb and `is_blocked`), `ApiKeyHeaderExtractor` (regex `^Bearer (lb_[A-Za-z0-9]{40})$`), `ApiKeyGenerator::hash()` (SHA-256 hex), and the finding history that shapes this design: libpq's `connect_timeout` has a floor of 2 seconds (a smaller value is treated as 2 — PostgreSQL 16 libpq connection parameters), a connect timeout and a statement timeout do not compose into a total deadline by themselves, and the "delayed connect + stalled statement" combination must be tested, not argued. The application's Doctrine connection (`config/packages/doctrine.yaml`) has no timeouts at all. The test suite runs the `prod` kernel through `HealthTest::bootProdKernel()` (cache cleared, `bootKernel(['environment' => 'prod', 'debug' => false])`, requests handled directly); the prod kernel reads `DATABASE_URL` without the `_test` suffix, i.e. the `app` database, which CI creates but does not migrate (`make test-db EXEC=` migrates only `app_test`). Existing fixtures spawn helper processes (`tests/Fixture/consume-limiter.php`, `create-api-key.php`).

## Goals / Non-Goals

**Goals:** a `prod` deep probe a monitor can actually use; a verification whose worst-case duration is a number enforced by the code, not a sum hoped for; refusals that reveal nothing and cost nothing (fail-closed, identical 404); a probe that still reports a database outage to a monitor verified before the outage; every failure mode reproduced end to end through the `prod` kernel; the probe's own checks untouched.
**Non-Goals:** see proposal. Design-level: no second authentication stack — the authorizer reuses the extractor's regex and the hash function and nothing else from the firewall; no dependency on the ORM or the cache component on this path (both fail to construct exactly when the probe is needed); no configurability of the budget or the TTL (constants with tests, not knobs).

## Decisions

1. **`ProbeAuthorizer` outside the firewall, on the probe's own bounded clients.** `HealthController`, in `prod`, calls `ProbeAuthorizer::authorize(?string $authorizationHeader): bool` and runs the probe only on `true`; `false` keeps the existing 404 body. The authorizer lives in `src/Shared/Health/` with the probe because it shares the probe's operational stance: raw clients built per call from the DSNs, every I/O bounded, nothing from the ORM or the cache pools. It takes the header, matches `ApiKeyHeaderExtractor`'s regex (a non-matching header is a refusal before any I/O), hashes with `ApiKeyGenerator::hash()`, and runs the two steps below under one `Deadline`. Alternative — moving `/health` under the `api` firewall and using the `access_token` authenticator — rejected: the liveness probe must stay unauthenticated, and the firewall's token handler uses the ORM connection, which has no timeouts. Alternative — `ApiKeyRepositoryInterface::findActiveByHash` — rejected for the same reason (Gate 1 round 1 finding 3 of the previous change).
2. **`Deadline`: a monotonic budget that every step consumes.** `Deadline::start(float $seconds)` records `hrtime(true)`; `remaining(): float` returns seconds left (≥ 0); `expired(): bool`. `ProbeAuthorizer::BUDGET_SECONDS = 4.0`. Each step asks the deadline for its allowance *before* it starts and is skipped when the allowance is below its floor, so the authorization as a whole can never exceed the budget by more than one step's overrun: the database connect is bounded by libpq (2 s floor — the connect step is skipped when less than 2.0 s remains, because libpq would silently wait 2 s anyway), the statement by `statement_timeout = min(2000, remaining × 1000)` ms, the Redis steps by `min(1.0, remaining)` s connect and read timeouts. Worst case: 2 s connect + up to 2 s statement + ≤ 0 s left for Redis → refusal at ≈ 4 s; the controller adds only formatting, so the 404 leaves within the spec's 5 seconds. `hrtime` is monotonic; the wall clock is used only for `expires_at`. Alternative — `pcntl_alarm`/`set_time_limit` — rejected: not available or not meaningful under PHP-FPM, and they abort instead of refusing.
3. **Step 1 — the database, on `BoundedDatabaseConnection::open(string $url, int $connectTimeoutSeconds, int $statementTimeoutMs): \PDO`.** The probe's `databaseConnection()` is refactored onto this factory (called with 2 and 2000, so `HealthProbeTest` keeps passing unchanged), the authorizer calls it with `2` and `min(2000, (int) (remaining × 1000))`. One statement: `SELECT u.roles, u.is_blocked, k.revoked_at, k.expires_at FROM api_keys k JOIN users u ON u.id = k.user_id WHERE k.key_hash = :hash` (indexed by the unique hash). Outcomes are three-valued on purpose: **verified** (row exists, `revoked_at IS NULL`, `expires_at IS NULL OR > now`, `is_blocked = false`, `roles` contains `ROLE_ADMIN`) → remember (step 3) and return `true`; **denied** (no row, or a row failing any condition — the database *answered*) → forget (step 3) and return `false`; **unavailable** (`\PDOException` on connect or query, statement timeout, malformed URL, skipped for lack of budget) → `warning` "deep probe authorization: database unavailable" `{exception class}` and fall through to step 2. `now` for the expiry check is the request's clock reading. The connection is closed after the statement. Alternative — one shared long-lived connection — rejected: a per-request connect is the price of a bounded connect timeout and of observing a dependency that is down.
4. **Step 2 — the Redis memory, on `BoundedRedisConnection::open(string $url, float $timeoutSeconds): \Redis`.** The probe's `checkRedis()` is refactored onto this factory (2.0 s). Key `probe-auth:<sha256 of the key hash>` — hashing the hash so the stored key names nothing that could be replayed if Redis were read — value `1`, TTL `ProbeAuthorizer::MEMORY_TTL_SECONDS = 300`. **Remember** after a verified step 1 (`SET … EX 300`), **forget** after a denied step 1 (`DEL`), **consult** only when step 1 was *unavailable*: `EXISTS` → `true` authorizes the probe (which will then report `database: fail`), `false` refuses. Redis failures in any of the three are a `warning` "deep probe authorization: memory unavailable" `{exception class}` and count as "not remembered" — never as verified. Consulting the memory only on database *unavailability* is what keeps revocation immediate whenever the database answers: a remembered hash cannot outlive a negative answer. Alternative — consult Redis first for speed — rejected: it would make revocation lag by up to 300 s in the normal case; the indexed lookup costs milliseconds. Alternative — remembering in APCu or a local file — rejected: per-process and per-node, and unavailable to a second container. Alternative — no memory at all (the previous plan) — rejected as the "convenient" design: it makes the deep probe blind to the one outage that matters most.
5. **Refusals are one body.** The controller keeps the existing 404 problem body and `Cache-Control: no-store` for every `false`; the authorizer's reason exists only in the `warning` (failure class, never the key, hash or prefix) and in the tests' timing assertions. No `WWW-Authenticate`, no `Retry-After`: the endpoint does not admit it is protected.
6. **Test fixtures for the failure modes** (`tests/Fixture/`): `black-hole-socket.php` — listens on 127.0.0.1:<port>, accepts connections and never writes, so libpq waits for the handshake until `connect_timeout` (2 s) fires; `tcp-delay-proxy.php` — listens on 127.0.0.1:<port>, on each connection sleeps <delay> seconds, then connects to PostgreSQL and pipes bytes both ways (`stream_select` loop) — a connection that completes late; both started with `Process` and stopped in `finally`, ports chosen by binding to port 0 and printing the assigned one. The prod kernel under test reads `DATABASE_URL` from `$_SERVER`/`$_ENV`; the tests set it to the fixture's address for that kernel (the way `bootProdKernel` overrides `COUNTRY_RESOLVERS`) and restore it afterwards. A stalled statement is produced with `LOCK TABLE api_keys IN ACCESS EXCLUSIVE MODE` in an open transaction on a second connection held by the test. The database outage for the "remembered monitor" case is the closed port again — after a first request against the real database has remembered the key.
7. **Prod-kernel tests need the schema in `app`.** `tests/Api/HealthDeepProdTest.php` inserts an admin user and keys into the `app` database through a bounded PDO of its own (committed rows, removed in `finally`); CI gains `make migrate EXEC=` before `make test-db EXEC=` so `app` carries `api_keys` — the same command a deployment runs. Alternative — pointing the prod kernel at `app_test` — rejected: the health tests deliberately probe the configured dependency as is.
8. **Tests.** *Unit*: `Deadline` (remaining decreases, never negative, `expired`), `ProbeAuthorizer` with fake step results (verified → true + remember; denied → false + forget; unavailable + remembered → true; unavailable + not remembered → false; unavailable + memory unavailable → false; a header that is not a key → false with no I/O; budget exhausted → false without touching Redis). *Integration* (`tests/Integration/Shared/Health/ProbeAuthorizerTest.php`, real PostgreSQL and Redis, spy logger): verified admin key → true and `EXISTS probe-auth:…` = 1; non-admin / blocked / revoked / expired / unknown → false and the memory key absent; unreachable `DATABASE_URL` → false within 3 s with the "database unavailable" warning; `SELECT pg_sleep(10)` through `BoundedDatabaseConnection::open(url, 2, 1000)` cancelled within ≈1 s; `BoundedRedisConnection::open` against a closed port fails within its timeout. *Api* (`HealthDeepProdTest`, prod kernel): the refusal matrix with identical bodies and unchanged `last_used_at`; the admin key → probe body; closed port → 404 fast (< 1 s); black-hole socket → 404 in 2–3 s; `LOCK TABLE` → 404 in 2–3 s; delay proxy (1.5 s) + `LOCK TABLE` → 404 under 5 s; remembered key + closed port → 503 with `database: fail`; revoked key after remembering → 404, and the memory key gone. Failing inputs, recorded in the commit bodies: the `roles` check removed → the non-admin case gets the probe body; the `is_blocked` check removed → the blocked-admin case gets it; the statement timeout not applied → the `LOCK TABLE` case misses 5 s; the connect step not skipped when < 2 s remain → the combined case misses 5 s; the `EXISTS` consulted on a *denied* answer → the revoked-after-remembering case gets the probe body; `DEL` on denial removed → same case fails once the database is closed; `SET … EX` removed → the remembered-monitor case gets 404; the 404 body built differently for lookup failures → the identical-body assertion fails.
9. **Logging and personal data.** Two `warning` records, `{exception}` only. The key, its hash and its prefix never appear in a log line, a response or an exception message the controller could echo. `last_used_at` is not written by the authorizer — its statement is a `SELECT`.

## Applicability (high tier)

| Question | Applies? | Note |
|---|---|---|
| Crash before/after an external effect | yes | The only writes are the Redis `SET … EX 300` after a verified lookup and the `DEL` after a denied one. A crash between the database answer and the Redis write leaves the memory stale by at most 300 s (remember) or leaves a stale memory that the next database answer deletes (forget); a crash between authorization and the probe costs one probe run. The database path is a `SELECT`. |
| Concurrent writers | n/a for correctness | Concurrent requests race only on the Redis key: any order of `SET`/`DEL` converges to the last database answer, and a `DEL` losing to a `SET` from a *concurrent verified* answer means the key was still valid at that instant. No lock. |
| Money rounding | n/a | — |
| Empty/zero/null inputs | yes | No header, an empty header, `Bearer` alone, a key of the wrong length or alphabet → refused before any I/O (the regex); a `roles` array without `ROLE_ADMIN` or a malformed `roles` value → denied; `expires_at` null → never expires; a budget already exhausted when a step starts → the step is skipped, never run with a zero timeout. |
| Authorization boundary | yes | The only path into the probe in `prod` is a database-verified, unrevoked, unexpired key of an unblocked admin, or the ≤ 300-second memory of exactly such a verification while the database is unavailable; every refusal is the same 404; the firewall, voters and the API-key resource are untouched. Failing inputs in decision 8. |
| Deletion/expiry | yes | Revocation, expiry, blocking and demotion are denied answers that also forget the memory — immediate while the database is up; during a database outage a revoked key's memory survives at most 300 s (documented trade-off). A deleted user cascades the key; the memory then expires by TTL. |
| Idempotency of retries | yes | Every authorization is a read (plus an idempotent `SET`/`DEL`); a monitor retrying after a 404 changes nothing; the probe itself is read-only. |

## Risks / Trade-offs

- [A revoked monitor key keeps deep-probe access for ≤ 300 s while the database is down] → the price of a probe that can report the outage; bounded by the TTL, immediate again once the database answers; the probe is read-only diagnostics; stated in the spec and the how-to.
- [The authorization adds up to 4 s to a monitor's request when the database is slow] → only in failure modes, where the monitor's alert is the point; a healthy lookup costs milliseconds; the monitor's own timeout should be ≥ 10 s (how-to).
- [libpq's 2-second connect floor makes the budget coarse] → the deadline skips the connect when < 2 s remain rather than pretending a shorter timeout; the budget of 4 s was chosen to fit exactly two floors plus the statement.
- [Two raw clients per authorized probe request (plus the probe's own two)] → four short connections per monitor poll (every 30–60 s); negligible; no pooling on purpose (decision 3).
- [Redis down as well as the database] → nothing to remember, fail-closed 404 within the budget; liveness `/health` is unaffected; the monitor alerts on non-200 regardless.
- [Fixture processes (black hole, delay proxy) in the suite] → small, single-file, started per test and stopped in `finally`; the same pattern as the limiter fixtures.
- [`make migrate EXEC=` in CI migrates `app`] → what a deployment does; adds seconds to CI.

## Migration Plan

No schema change. Deploy: code only; a monitor sets `Authorization: Bearer <admin key>` on its deep-probe request and alerts on any non-200. Rollback: remove the code; `?deep=1` in `prod` is unconditionally 404 again; stale `probe-auth:*` keys in Redis expire within 300 s.
