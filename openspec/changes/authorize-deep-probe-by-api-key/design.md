# Design — authorize-deep-probe-by-api-key

## Context

See `proposal.md` — Why. State: `HealthController` (`src/Shared/Health/`) answers `GET /health` (liveness) and `GET /health?deep=1` through `HealthProbe`, which deliberately builds its own raw clients from `DATABASE_URL` / `REDIS_URL` rather than the application's Doctrine connection or cache pool: a PDO with `ATTR_TIMEOUT` 2 s (pdo_pgsql maps it to libpq's `connect_timeout`) and `options='-c statement_timeout=2000'`, and an ext-redis client with 2-second connect and read timeouts; `HealthProbeTest` proves both bounds against a responsive server. In `prod` the controller returns a hand-built 404 problem body with `Cache-Control: no-store` for `?deep=1`. `/health` is `PUBLIC_ACCESS`, outside every firewall and the OpenAPI document. The archived change `add-api-keys-and-rate-limiting` left in `main`: `api_keys` (`key_hash` char(64) unique, `expires_at`, `revoked_at`, `user_id` → `users` with `roles` jsonb and `is_blocked`), `ApiKeyHeaderExtractor` (regex `^Bearer (lb_[A-Za-z0-9]{40})$`), `ApiKeyGenerator::hash()` (SHA-256 hex).

Constraints established by review (previous change's Gate 1 and this change's round 1 and confirmation 1): (1) no in-process PostgreSQL client PHP offers can be bounded by the caller through to *cleanup* — a synchronous PDO call blocks on a lost response; ext-pgsql's asynchronous API bounds the receive loop but its cancellation and close (`pg_cancel_query`, `pg_close`, the resource destructor) drain `PQgetResult` and therefore block on the same lost response (PHP 8.4 `ext/pgsql`, libpq asynchronous processing). (2) libpq's `connect_timeout` floor is 2 seconds. (3) Host-name resolution precedes every timeout and is bounded only by the resolver — the probe's existing contract already states this. (4) Ordering a memory by `clock_timestamp()` is unsound: the timestamp is evaluated when the expression runs, not when the statement's snapshot was taken, so a request paused between snapshot and evaluation can carry a stale row with a later time. (5) A reserved consultation allowance is needed for the outage report to be reachable (confirmed in confirmation 1).

What the runtime offers, verified in the container: `proc_open` is available (`pcntl` is not); Symfony `Process::checkTimeout()` calls `stop(0)` — SIGTERM, then SIGKILL immediately because the grace period is zero — and throws `ProcessTimedOutException` (`vendor/symfony/process/Process.php`); a console kernel boot costs ≈0.6 s in dev, so the child must not boot the kernel. ext-redis bounds each read with `OPT_READ_TIMEOUT` and the connect with the `connect()` timeout; Redis executes commands one at a time, so `GET`/`EVAL` from concurrent clients are totally ordered. PostgreSQL READ COMMITTED takes a fresh snapshot per statement, and a single-statement autocommit `SELECT` sees every transaction committed before the statement started. The test suite runs the `prod` kernel through `HealthTest::bootProdKernel()`; the prod kernel reads `DATABASE_URL` without the `_test` suffix (the `app` database), which CI creates but does not migrate. Existing fixtures spawn helper processes (`tests/Fixture/consume-limiter.php`, `create-api-key.php`).

## Goals / Non-Goals

**Goals:** a `prod` deep probe a monitor can use; a verification whose worst-case duration — including whatever cleanup a stuck client needs — is enforced by a mechanism the caller controls; refusals that reveal nothing and cost nothing; a probe that still runs for a monitor verified before a database outage, with a memory whose ordering follows the *order in which answers were observed*, not clocks or snapshots, and whose failure modes are stated; every failure mode reproduced end to end through the `prod` kernel.
**Non-Goals:** see proposal. Design-level: no second authentication stack (only the extractor's regex and the hash function are reused); no ORM or cache component on this path; no configurability of the allowances or the TTL; the probe's own checks are not rewritten in this change (their lost-response gap is recorded in Risks as a follow-up candidate).

## Decisions

1. **`ProbeAuthorizer` outside the firewall.** `HealthController`, in `prod`, calls `ProbeAuthorizer::authorize(?string $authorizationHeader): bool` and runs the probe only on `true`; `false` keeps the existing 404 body. The authorizer matches the header against `ApiKeyHeaderExtractor`'s regex (no match → refusal before any I/O), hashes with `ApiKeyGenerator::hash()`, then runs the database phase (decision 3) and the memory phase (decision 4) under the allowances of decision 2. Alternatives rejected as before: `/health` under the firewall (liveness must stay open; the firewall's handler uses the unbounded ORM connection); the repository (unbounded).
2. **Two phases with fixed allowances.** `ProbeAuthorizer::DATABASE_ALLOWANCE = 2.5` s and `REDIS_ALLOWANCE = 1.0` s (reserved: the memory phase always gets it — confirmation 1, finding 3), 3.5 s of I/O in all; the refusal leaves within the spec's 5 seconds. The Redis work of one request is exactly four operations on one connection — connect, `AUTH` (when the DSN has a password; otherwise a `PING` takes its slot so the count is fixed), the pre-lookup `GET` of the generation token, and one post-lookup command (the `EVAL` that remembers, the `EVAL` that denies, or the `GET` that consults) — each with `REDIS_ALLOWANCE / 4 = 0.25` s as its connect or read timeout, so the phase never exceeds 1.0 s however slow every operation is (confirmation 2, finding 1). The connect, `AUTH` and the generation `GET` run *before* the database phase, the one post-lookup command after it, on the same connection; the total I/O is therefore ≤ 2.5 + 1.0 = 3.5 s in every mode, the post-lookup command always has its 0.25 s, and a Redis failure before the lookup (connect, `AUTH` or the generation read) makes the request "memory unavailable" for its whole duration — the lookup still runs and a verified answer is still honoured for this request, only not remembered. Host-name resolution is outside both allowances (Context, constraint 3); the how-to recommends IP literals or a local resolver for the two DSNs where the resolver may stall.
3. **The database phase is a child process killed at its deadline — `KeyLookupProcess`.** The lookup runs in `bin/probe-key-lookup`, a standalone PHP script (no kernel: `require vendor/autoload.php` for nothing but PDO is unnecessary — the script uses plain `PDO` and `getenv`), started by `Symfony\Component\Process\Process` with `setTimeout(DATABASE_ALLOWANCE)`, `DATABASE_URL` passed in the child's environment, the key hash written to the child's **stdin** (never argv or env — `ps` must not show it). The child connects with pdo_pgsql (`ATTR_TIMEOUT` 2 s, `statement_timeout` = the allowance in ms as the belt), runs one statement — `SELECT u.roles, u.is_blocked, k.revoked_at, k.expires_at FROM api_keys k JOIN users u ON u.id = k.user_id WHERE k.key_hash = :hash` — and prints exactly one line: `V <expires_at RFC 3339 or ->` (verified: row present, `revoked_at IS NULL`, not expired at the child's `now`, `is_blocked = false`, `roles` contains `ROLE_ADMIN`), `D` (denied: no row, or a row failing a condition — the database *answered*), or `U <exception class>` (unavailable: connect or query failed). The parent maps the exit: a clean `V`/`D`/`U` line → that outcome; a `ProcessTimedOutException` (the child was SIGKILLed with its blocked libpq call, its socket closed by the kernel — no PHP cleanup runs in the parent), a non-zero exit, or unparsable output → **unavailable** with a `warning` "deep probe authorization: database unavailable" `{reason class}`. This is the only mechanism in PHP that bounds the *whole* operation including a stuck client's teardown: the operating system reclaims the process. Cost: one `proc_open` and a ≈20-ms PHP start per monitor poll, without a kernel boot. Alternative — ext-pgsql's asynchronous API — rejected (Context, constraint 1: cleanup blocks on `PQgetResult`). Alternative — a hand-written wire-protocol client over PHP streams — rejected: SCRAM authentication and protocol handling are security-sensitive code with no portfolio value. Alternative — `pcntl_alarm` — unavailable under FPM.
4. **`ProbeMemory` ordered by a generation *token* that never repeats.** Redis holds, per key hash `h` (`sha256(h)` in the key names): `probe-auth:gen:<h>` — a random 128-bit token (16 bytes from `random_bytes`, hex) that every **denied** answer *replaces* (never increments: confirmation 2, finding 2 — an integer counter with a TTL can be recreated at the same value after it expires, so equality no longer proves "nothing was denied since I looked"), and `probe-auth:v:<h>` — a JSON `{"gen":<token or "">,"exp":<expires_at or null>,"verified_at":<request wall clock, RFC 3339>}`. Two Lua scripts, each one `EVAL`: **remember** stores the value with a 300-second TTL *only if* the current token equals the one the authorizer read before its lookup (absent counts as `""`, and an absent key only matches an absent read); **deny** sets a fresh random token (TTL 300 s) and deletes `v` in the same script. Ordering argument (confirmation 1, finding 2, now without reuse): a stale verification is one whose lookup statement's snapshot predates a revocation R; a denial D that observed R runs after R, so its `EVAL` runs after the stale request's pre-lookup `GET` (the `GET` happened before that request's statement, whose snapshot predates R — a `GET` after D would give a statement snapshot after R, which would see the revocation); Redis orders D's `EVAL` after the `GET`, so at the stale request's CAS the current token is D's fresh random value, which cannot equal the token read before — not by increment, not by recreation after expiry; the CAS refuses. If the token merely expired between the read and the write with no denial, the CAS also refuses (absent ≠ read) — a harmless false negative: the verification is simply not remembered until the next request. **Consult** (only when the database phase is unavailable): `GET v` → authorize iff present, `verified_at` is within `MEMORY_TTL_SECONDS = 300` of the request's wall clock (the age bound is anchored to the verification, not to when the write landed — a delayed write does not extend it), and `exp` is null or in the future. Every Redis failure → `MemoryUnavailable` naming the operation that failed (`connect`, `auth`, `token`, `remember`, `deny`, `consult`) → `warning` "deep probe authorization: memory unavailable" `{operation, exception class}`, and counts as "not remembered"/"not written"; the named operation is what the fixture tests assert on. **Admitted case (unchanged):** if Redis is unreachable at the moment of a denial, the token is not replaced and `v` not deleted, so an earlier `v` survives until its `verified_at` is 300 s old — stale authorization during a database outage bounded by that age, stated in the spec, logged at `warning`. Alternatives rejected: `clock_timestamp()` (snapshot-unsound), an integer generation with TTL (recurs), `revision` columns on two tables (no total order between them).

5. **The outage report is the probe's own.** When a remembered monitor is authorized during database unavailability, the probe runs unchanged and reports what *it* observes: a refused or unreachable database → `503` with `database: fail`; a database that answers `SELECT 1` but had `api_keys` locked or a lookup that stalled → possibly `database: ok`. The spec promises "the probe runs and reports its own checks", not a status.
6. **Refusals are one body.** The controller keeps the existing 404 problem body and `Cache-Control: no-store` for every `false`; no `WWW-Authenticate`, no `Retry-After`. The reason exists only in the `warning` and in the tests' timing assertions.
7. **Fixtures** (`tests/Fixture/`): `black-hole-socket.php` (binds 127.0.0.1:0, prints the port, accepts, never writes — a connection that never completes); `tcp-proxy.php` (binds 127.0.0.1:0, prints the port; `--upstream=host:port`, `--delay=<s>` before connecting upstream, `--stall-after-responses=<n>` forwards upstream→client for the first *n* upstream messages then swallows everything upstream sends while still forwarding client→upstream — a completed handshake followed by a lost response); `fake-redis-server.php` (binds 127.0.0.1:0, prints the port; speaks enough RESP to answer `AUTH`/`PING` with `+OK`/`+PONG`, `GET` with `$-1`, `EVAL` with `+OK`, each after `--response-delay=<s>`, and with `--slow-from-command=<n>` only from the n-th RESP command on — the wire carries exactly three commands per request (`AUTH`/`PING` = 1, the token `GET` = 2, the post-lookup command = 3; the TCP connect is not a command — confirmation 3), so `--slow-from-command=3` keeps `AUTH` and the token read fast and delays only the *post-lookup* command; appends every command it received and answered, with timestamps, to `--command-log=<file>`, so a test asserts which commands completed rather than inferring it from timing; `--get-value=<string>` answers `GET` with that bulk string instead of a null bulk, which is how a slow-but-answering Redis serves a remembered verification); `full-backlog-listener.php` (binds 127.0.0.1:0 with `listen(0)`, connects to itself once and never accepts, prints the port — the accept queue is full, so the kernel drops the next SYN and a client's connect stalls until the client's own connect timeout; a delayed `accept` would not do, because an established connection waits in the queue and only the first read stalls — confirmation 3). All run with `Process`, stopped in `finally`, ports from bind-to-0. A stalled *statement* on a responsive server is `LOCK TABLE api_keys IN ACCESS EXCLUSIVE MODE` in an open transaction on the test's own connection. The prod kernel under test runs in a process of its own (`prod-health-request.php`, driven by `ProdHealthRequest`): the DSNs are that process's environment — no test can leak them into another — and the prod log handlers write to its stderr, which is how a test reads the warnings the identical 404 withholds. It prints the status, headers, body and the seconds the kernel took as one JSON line. `var/cache/prod` is removed once per test process (the prod container is cached without resource tracking) and reused by every child.
8. **Prod-kernel tests need the schema in `app`.** `HealthDeepProdTest` inserts the admin user and keys into the `app` database through a bounded PDO of its own (committed, removed in `finally`); CI gains `make migrate EXEC=` before `make test-db EXEC=`.
9. **Tests.** *Unit*: `ProbeAuthorizer` with the two phases faked — verified → true + remember(token read before); denied → false + deny; unavailable + `v` present and unexpired → true; unavailable + `v` expired by `exp` → false; unavailable + no `v` → false; unavailable + Redis failing → false; a non-key header → false with no I/O; a database phase reported as timed out still consults the memory; `KeyLookupProcess` output parsing (`V …`, `D`, `U …`, garbage → unavailable). *Integration* — `KeyLookupProcessTest` (real PostgreSQL + fixtures): admin key → `V` with the key's expiry; non-admin / blocked / revoked / expired / unknown → `D`; closed port → `U` at once; black-hole connect → `U` within the allowance (the child killed at 2.5 s, or libpq's 2-second connect timeout first); `LOCK TABLE` → `U` at the allowance with the child killed and no lingering process (`ps` shows no `probe-key-lookup` after the call); proxy `--stall-after-responses=1` (handshake done, response lost) → `U` at the allowance, child killed — the case no in-process client passes; the hash is not in the child's command line (`ps` on the running child during the `LOCK TABLE` case shows no hash). `ProbeMemoryTest` (real Redis): `remember(token)` stores only when the token is current (absent matches only an absent read); `deny` replaces the token with a fresh random one — two denials give two different tokens — and deletes `v`; TTLs ≤ 300 s; the interleaving **established by the real mechanism**, both requests being the real `ProbeAuthorizer`: A's lookup is wrapped so that the revocation and B's full `authorize()` (denied → new token, `v` deleted) happen after A's database answer and before A reaches its memory write — A's own token read already preceded its statement, so nothing about the order is supplied by the test; A is honoured for its own request and its verification is refused, `v` absent; **the reuse case**: the same wrapping with a denial's token X read first and the token key deleted inside the window (standing for TTL expiry) — B's denial creates Y ≠ X and A's write is refused; **the age bound**: a `v` written with `verified_at` 301 s ago (test-injected clock) is not consulted even though its TTL has not run out; the fake Redis with a password: `--response-delay=0.2` on every command → `AUTH`, the token `GET` and the post-lookup command all succeed — the command log lists all three as answered, the Redis time is ≥ 0.6 s and the whole phase stays within 1.0 s; `--slow-from-command=3 --response-delay=0.5` → the command log shows `AUTH` and the token `GET` answered and the post-lookup command received but not yet answered, `MemoryUnavailable(operation: consult)` (the database phase pointed at a closed port; `remember` in the variant with a live database) raised after ≥ 0.25 s and < 0.5 s — the assertion pins the operation and the log pins the earlier commands, so an ordinary "nothing remembered" 404 cannot pass it; the full-backlog listener as the Redis address → `MemoryUnavailable(operation: connect)` after ≥ 0.25 s and < 0.5 s with an empty command log, and the request still runs its database phase — a verified key is honoured for this request and not remembered. `ProbeAuthorizerTest` (real PostgreSQL and Redis, spy logger): admin key → true and `v` present; non-admin / blocked / revoked / expired / unknown → false, token replaced, `v` absent; closed port → false within 3 s with the "database unavailable" warning; `LOCK TABLE` → false within 3 s; a remembered `v` + closed port → true; after a denial + closed port → false; Redis unreachable during a denied answer → false, the "memory unavailable" warning, and the earlier `v` still present (the admitted case, asserted as such). *Api* (`HealthDeepProdTest`, prod kernel): the refusal matrix with identical bodies and unchanged `last_used_at`; admin key → probe body; closed port → 404 under 1 s; black-hole connect → 404 under 3.5 s; `LOCK TABLE` → 404 in 2.5–4 s; proxy `--delay=0.7` + `LOCK TABLE` → 404 under 5 s; proxy `--stall-after-responses=1` → 404 under 5 s; database closed + fake Redis with `--response-delay=0.5` → 404 under 5 s; remembered key + closed port → 503 `database: fail`; remembered key + `LOCK TABLE` → the probe runs (200 expected); revoked while the database is up, then closed port → 404. Failing inputs, recorded in the commit bodies: the `roles` check removed → the non-admin case gets the probe body; the `is_blocked` check removed → the blocked-admin case gets it; `setTimeout` removed from the child process → the lost-response case exceeds 5 s (the parent waits on the child); the token read moved *after* the database phase → the established-interleaving test stores the stale `v`; the CAS replaced by a plain `SET` → the same test stores it; the random token replaced by an incrementing counter → the reuse case stores the stale `v`; the `verified_at` bound removed → the 301-second-old `v` authorizes; the per-command Redis timeout removed (client defaults) → the slow post-lookup test observes the full 0.5 s delay instead of failing at 0.25 s, and the full-backlog test does not return within 0.5 s; `DEL` on denial removed → the "after a denial + closed port" case authorizes; the `exp` check at consult removed → an expired remembered key authorizes; the reserved Redis allowance replaced by "skip when the database phase used its allowance" → the remembered-monitor + `LOCK TABLE` case answers 404; the 404 body built differently on a lookup failure → the identical-body assertion fails.
10. **Logging and personal data.** Two `warning` records on a `health` Monolog channel of their own (`#[WithMonologChannel('health')]`, an always-on stderr handler in `prod`: the main handler is `fingers_crossed` and would drop a warning whose response is a 404), `{reason}` for the database and `{operation, exception}` for the memory — class names only. The key, its hash and its prefix never appear in a log line, a response, the child's command line or an exception message the controller could echo. The authorizer never writes `last_used_at` — the child's statement is a `SELECT`.

## Applicability (high tier)

| Question | Applies? | Note |
|---|---|---|
| Crash before/after an external effect | yes | The only writes are the deny `EVAL` (new token + `DEL`) and the remember `EVAL` (CAS). A crash between the database answer and the write leaves the memory one answer behind — a missed deny `EVAL` is the admitted staleness (≤ 300 s from the verification); a missed verification write only delays the memory. A child killed at its deadline leaves no state (a `SELECT`). |
| Concurrent writers | yes | Requests race on the two Redis keys; Redis totally orders their commands, and the random token read *before* each request's statement makes a stale verification's write fail the CAS whenever a denial was observed between — including across the token's expiry, because a recreated token is a fresh random value (decision 4's argument, tested by the established interleaving and the reuse case). What no ordering fixes is a write that never reached Redis — the admitted case, logged and bounded. |
| Money rounding | n/a | — |
| Empty/zero/null inputs | yes | No header, `Bearer` alone, a wrong-shaped key → refused before any I/O; `roles` without `ROLE_ADMIN` or malformed → `D`; `expires_at` null → never expires (`exp` null in the memory); a child that prints nothing, garbage or exits non-zero → unavailable; a memory value that is not the expected JSON → not remembered. |
| Authorization boundary | yes | The only path into the `prod` probe: a database-verified unrevoked, unexpired key of an unblocked admin, or a `v` memory of such a verification less than 300 s old (by `verified_at`) that no later denial superseded and whose key has not expired, while the database phase is unavailable; every refusal is the same 404; the firewall, voters and the API-key resource are untouched; the hash never reaches a command line. Failing inputs in decision 9. |
| Deletion/expiry | yes | Revocation, blocking and demotion are denied answers that replace the token and delete `v` — immediate while the database and Redis are up; expiry is checked from `exp`, and the verification's age from `verified_at`, at consult time even during an outage; a deleted user cascades the key and the memory expires by TTL. |
| Idempotency of retries | yes | Every authorization is a read plus idempotent Redis writes; a monitor retrying after a 404 changes nothing; the probe is read-only. |

## Risks / Trade-offs

- [A revoked monitor key keeps deep-probe access for ≤ 300 s from its verification while the database is down, when Redis was unreachable at the moment of the denial] → the price of a probe that can report the outage; bounded by the verification's age; the probe is read-only diagnostics; stated in the spec and the how-to.
- [The probe's own checks still use synchronous clients] → their responsive-server bounds hold (`HealthProbeTest`); a lost response after the handshake would hang the probe's database check; recorded as a follow-up (the check can run through `KeyLookupProcess`'s sibling — a `SELECT 1` child with the same kill deadline), deliberately not folded into this change.
- [A process spawn per monitor poll] → ≈20 ms of PHP start without a kernel, every 30–60 s; `proc_open` must be allowed in the deployment's PHP configuration (it is in the image; the how-to says so).
- [The child is killed with a blocked libpq call] → the kernel closes its socket; PostgreSQL notices the dead client at the next write or by TCP keepalive and ends the session — no lock is held (a `SELECT` without `FOR …`).
- [Host-name resolution is outside the allowances] → the probe's existing exclusion; the how-to recommends IP literals or a local resolver.
- [Redis unreachable before the lookup (connect, `AUTH` or the token read)] → the request still verifies against the database and honours a verified answer for itself; it only cannot remember it; a `warning` says so.
- [The full-backlog listener depends on Linux dropping SYNs when the accept queue is full (`tcp_abort_on_overflow=0`, the default; the container is Linux)] → the test asserts the connect operation and its timing, so a kernel that refused instead would fail it visibly rather than pass it silently.
- [Fixture processes in the suite] → small single-file scripts, started per test, stopped in `finally`, ports from bind-to-0.

## Migration Plan

Code only (no schema change, no new extension): `bin/probe-key-lookup` ships with the code and must be executable; a monitor sets `Authorization: Bearer <admin key>` on its deep-probe request and alerts on any non-200. Rollback: remove the code; `?deep=1` in `prod` is unconditionally 404 again; `probe-auth:*` keys expire within 300 s.
