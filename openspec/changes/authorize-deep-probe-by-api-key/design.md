# Design — authorize-deep-probe-by-api-key

## Context

See `proposal.md` — Why. State: `HealthController` (`src/Shared/Health/`) answers `GET /health` (liveness) and `GET /health?deep=1` through `HealthProbe`, which deliberately builds its own raw clients from `DATABASE_URL` / `REDIS_URL` rather than the application's Doctrine connection or cache pool: a PDO with `ATTR_TIMEOUT` 2 s (pdo_pgsql maps it to libpq's `connect_timeout`) and `options='-c statement_timeout=2000'`, and an ext-redis client with 2-second connect and read timeouts; `HealthProbeTest` proves both bounds against a responsive server. In `prod` the controller returns a hand-built 404 problem body with `Cache-Control: no-store` for `?deep=1`. `/health` is `PUBLIC_ACCESS` in `access_control`, outside every firewall and the OpenAPI document. The archived change `add-api-keys-and-rate-limiting` left in `main`: `api_keys` (`key_hash` char(64) unique, `expires_at`, `revoked_at`, `user_id` → `users` with `roles` jsonb and `is_blocked`), `ApiKeyHeaderExtractor` (regex `^Bearer (lb_[A-Za-z0-9]{40})$`), `ApiKeyGenerator::hash()` (SHA-256 hex).

What the reviews of the previous change and of this change's round 1 established, and this design takes as constraints: (1) a *synchronous* PDO call cannot be bounded by the client once the handshake is done — a server-side `statement_timeout` cancels execution on the server, but if the transport stops delivering (a proxy or network that swallows the response) the blocking client waits forever, and no `Deadline` check before the call can interrupt it; pdo_pgsql exposes no read timeout. (2) libpq's `connect_timeout` has a floor of 2 seconds. (3) Host-name resolution happens before any timeout and is bounded only by the platform resolver — the existing health-check spec already states this exclusion for the probe. (4) `SET`/`DEL` on a memory key do not converge to the last database answer under interleaving, and a failed `DEL` leaves an entry behind. (5) A budget "consumed" by the database phase must not silently skip the consultation the outage report depends on.

PHP offers exactly one PostgreSQL client with a client-side deadline: the `pgsql` extension's asynchronous API — `pg_connect($dsn, PGSQL_CONNECT_ASYNC)` + `pg_connect_poll()` driven by `stream_select()` on `pg_socket()`, then `pg_send_query_params()` and `stream_select()` + `pg_consume_input()` + `pg_connection_busy()` until `pg_get_result()`, with `pg_cancel_query()` + `pg_close()` on a missed deadline — every wait is a `stream_select` with a timeout the caller computes. The extension is **not** in the image today (`php -m`: `pdo_pgsql`, `redis`; `.docker/php/Dockerfile` installs `pdo_pgsql intl opcache redis gd zip apcu`; CI `setup-php` lists `pdo_pgsql, intl, mbstring, redis, gd`) — it builds from the same libpq and is added in this change. ext-redis bounds every read with `OPT_READ_TIMEOUT` (per command) and the connect with the `connect()` timeout, so a Redis phase is bounded by connect + one timeout per command issued. The test suite runs the `prod` kernel through `HealthTest::bootProdKernel()`; the prod kernel reads `DATABASE_URL` without the `_test` suffix (the `app` database), which CI creates but does not migrate. Existing fixtures spawn helper processes (`tests/Fixture/consume-limiter.php`, `create-api-key.php`).

## Goals / Non-Goals

**Goals:** a `prod` deep probe a monitor can use; a verification whose worst-case duration is enforced by the client on every wait, including a lost response; refusals that reveal nothing and cost nothing; a probe that still runs for a monitor verified before a database outage, with a memory whose ordering follows the database's answers and whose failure modes are stated, not assumed; every failure mode reproduced end to end through the `prod` kernel.
**Non-Goals:** see proposal. Design-level: no second authentication stack (only the extractor's regex and the hash function are reused); no ORM or cache component on this path; no configurability of the budget or the TTL; the probe's own two checks are not rewritten onto the async client in this change (their lost-response gap is recorded in Risks as a follow-up candidate, not silently closed here).

## Decisions

1. **`ProbeAuthorizer` outside the firewall, on clients the caller can bound on every wait.** `HealthController`, in `prod`, calls `ProbeAuthorizer::authorize(?string $authorizationHeader): bool` and runs the probe only on `true`; `false` keeps the existing 404 body. The authorizer lives in `src/Shared/Health/` with the probe and shares its stance — raw clients from the DSNs, nothing from the ORM or the cache pools, everything bounded — but on two new clients: `AsyncPostgresQuery` (decision 3) and `BoundedRedisCommands` (decision 4). It matches the header against `ApiKeyHeaderExtractor`'s regex (no match → refusal before any I/O), hashes with `ApiKeyGenerator::hash()`, and runs the phases of decision 2. Alternative — `/health` under the `api` firewall with the `access_token` authenticator — rejected: liveness must stay unauthenticated and the firewall's handler uses the ORM connection (no timeouts). Alternative — the previous plan's synchronous PDO with a statement timeout — rejected by the round-1 counterexample (a stalled transport after the handshake).
2. **Two phases with fixed allowances, not one shared budget.** `Deadline::start(float $seconds)` on `hrtime(true)`, `remaining()`, `expired()`. `ProbeAuthorizer::DATABASE_ALLOWANCE = 2.5` s, `REDIS_ALLOWANCE = 1.0` s (a **reserved** allowance the Redis phase always gets, whatever the database phase consumed — round 1, finding 3), total 3.5 s of I/O; with request handling the refusal leaves within the spec's 5 seconds. Inside the database phase the connect gets at most 1.0 s and the query the rest (the async client owns these deadlines; libpq's 2-second `connect_timeout` floor is irrelevant because the client, not libpq, times the connect). Inside the Redis phase each operation (connect, `AUTH`, one `EVAL` or `GET`) gets `REDIS_ALLOWANCE / 3` as its connect or read timeout, so the phase cannot exceed its allowance even with a password. Host-name resolution in either DSN is outside both allowances, exactly as the probe's own contract states — the how-to recommends IP literals or a local resolver for `DATABASE_URL`/`REDIS_URL` on hosts where the resolver may stall; the compose stack resolves service names locally. Alternative — one shared 4-second budget with steps skipped when exhausted — rejected: it is what made the outage report unreachable (finding 3).
3. **`AsyncPostgresQuery::selectOne(string $url, string $sql, array $params, Deadline $deadline): Outcome`** — ext-pgsql's asynchronous API: `pg_connect($dsn, PGSQL_CONNECT_ASYNC | PGSQL_CONNECT_FORCE_NEW)`, then `pg_connect_poll()` in a loop that waits on `pg_socket()` with `stream_select()` and the remaining connect allowance until `PGSQL_POLLING_OK` (or `FAILED`); `pg_send_query_params()`; then `stream_select()` on the socket with the remaining allowance, `pg_consume_input()`, until `!pg_connection_busy()`; `pg_get_result()` → one row or none. Any deadline hit → `pg_cancel_query()` (best effort, non-blocking) + `pg_close()` → **unavailable**. The DSN also carries `options='-c statement_timeout=<allowance ms>'` as the server-side belt for a responsive server; the client deadline is the guarantee for an unresponsive transport. The statement: `SELECT u.roles, u.is_blocked, k.revoked_at, k.expires_at, clock_timestamp() AS answered_at FROM api_keys k JOIN users u ON u.id = k.user_id WHERE k.key_hash = $1` — `answered_at` is the database's own time for the answer, used to order the memory (decision 4). Outcomes are three-valued: **verified** (row, `revoked_at IS NULL`, `expires_at IS NULL OR > now`, `is_blocked = false`, `roles` contains `ROLE_ADMIN`), **denied** (no row, or a row failing any condition — the database *answered*; `answered_at` from `SELECT clock_timestamp()` in the same statement even when no key row matches, via a `LEFT JOIN` from a one-row subselect), **unavailable** (connect or query failed or timed out, malformed URL) → `warning` "deep probe authorization: database unavailable" `{exception class}`. Alternative — a child process with a wall-clock kill — rejected: a process spawn per monitor poll and an abort instead of a refusal. Alternative — the PDO client with `statement_timeout` — the rejected round-1 plan.
4. **`BoundedRedisCommands` and a memory ordered by the database's clock.** `open(string $url, float $perOperationTimeout): \Redis` — the probe's ext-redis connect/AUTH factored out with `OPT_READ_TIMEOUT` set to the same value, so every command is bounded. The memory key `probe-auth:<sha256(key hash)>` holds a small JSON `{"s":"v"|"d","at":<answered_at as microseconds>}` with a 300-second TTL and is written by one Lua script (`EVAL`, atomic): *write `{s, at}` only if the key is absent or its stored `at` is older than the new `at`* — a compare-and-set on the database's answer time. **Remember** = CAS `{s: v, at}` after a verified answer; **forget** = CAS `{s: d, at}` after a denied answer (a marker, not a `DEL`, so a late verified write with an older `at` cannot resurrect access — round 1, finding 2's interleaving: A reads valid at t₁, revocation commits, B reads revoked at t₂ > t₁ and writes `d@t₂`, A's `v@t₁` arrives and is refused by the CAS); **consult** = `GET` only when the database phase was *unavailable*: authorize iff `s = v` and `at` is within `MEMORY_TTL_SECONDS = 300` of the request's wall clock (the lifetime is anchored to the verification's `answered_at`, not to when the write landed; the application and database clocks are assumed NTP-close — a skew shows as a shorter or longer memory, never as a different key). A Redis failure in remember/forget/consult is a `warning` "deep probe authorization: memory unavailable" `{exception class}` and counts as "not remembered". **Admitted case:** when Redis is unreachable at the moment of a *denied* answer, the marker is not written and an earlier `v` entry survives until its `at` is older than 300 s — up to 300 s of stale authorization *only if* a database outage follows within that window; the spec states this bound explicitly rather than promising an invalidation the transport cannot deliver. Alternative — `DEL` on denial — rejected (finding 2). Alternative — remembering in APCu or a file — rejected: per process and per node. Alternative — no memory — rejected: a probe that is blind to the outage it exists for.
5. **The outage report is the probe's own.** When a remembered monitor is authorized during database unavailability, the probe runs unchanged and reports what *it* observes: a refused or unreachable database → `503` with `database: fail`; a database that accepts `SELECT 1` but had `api_keys` locked or a lookup that stalled → the probe may report `database: ok`. The spec promises "the probe runs and reports its own checks", not a specific status (round 1, finding 3). The authorization failure and the dependency report stay distinct in logs: the `warning` names the authorization phase.
6. **Refusals are one body.** The controller keeps the existing 404 problem body and `Cache-Control: no-store` for every `false`; no `WWW-Authenticate`, no `Retry-After`. The reason exists only in the `warning` and in the tests' timing assertions.
7. **Fixtures** (`tests/Fixture/`): `black-hole-socket.php` (binds 127.0.0.1:0, prints the port, accepts, never writes — a connection that never completes); `tcp-proxy.php` (binds 127.0.0.1:0, prints the port; per connection: `--delay=<s>` sleeps before connecting upstream, `--stall-after-responses=<n>` forwards upstream→client for the first *n* upstream messages then swallows everything upstream sends while still forwarding client→upstream — a completed handshake followed by a lost response); both run with `Process`, stopped in `finally`. A stalled *statement* on a responsive server is `LOCK TABLE api_keys IN ACCESS EXCLUSIVE MODE` in an open transaction on the test's own connection. Redis stalls reuse the black hole (connects, never answers `AUTH`/`EVAL`/`GET`). The prod kernel under test reads `DATABASE_URL`/`REDIS_URL` from `$_SERVER`/`$_ENV`, set for that kernel and restored afterwards (the `bootProdKernel` pattern).
8. **Prod-kernel tests need the schema in `app`.** `HealthDeepProdTest` inserts the admin user and keys into the `app` database through a bounded client of its own (committed, removed in `finally`); CI gains `make migrate EXEC=` before `make test-db EXEC=`, and the `pgsql` extension in `setup-php`; the Dockerfile adds `pgsql` to `install-php-extensions`.
9. **Tests.** *Unit*: `Deadline`; `ProbeAuthorizer` with the two clients replaced by fakes — verified → true + remember; denied → false + forget; unavailable + remembered fresh → true; unavailable + remembered but older than 300 s → false; unavailable + denied marker → false; unavailable + not remembered → false; unavailable + Redis failing → false; a non-key header → false with no I/O; a database phase that consumed its whole allowance still gets the Redis phase. *Integration* (`ProbeAuthorizerTest`, real PostgreSQL and Redis, spy logger): admin key → true and the memory holds `v` with `at` ≈ now; non-admin / blocked / revoked / expired / unknown → false and the memory holds `d`; the CAS refuses an older write (`forget(at=t₂)` then `remember(at=t₁<t₂)` leaves `d`) and accepts a newer one; closed port → false within 3 s with the "database unavailable" warning; black-hole connect → false within 1.5 s (the 1.0-second connect allowance); `LOCK TABLE` → false within 3 s; post-handshake stall through the proxy (`--stall-after-responses=1`: the handshake completes, the query's response is swallowed) → false within 3 s — the case a PDO client cannot pass; Redis black hole → remember/consult fail within the per-operation timeout with the "memory unavailable" warning. *Api* (`HealthDeepProdTest`, prod kernel): the refusal matrix with identical bodies and unchanged `last_used_at`; admin key → probe body; closed port → 404 under 1 s; black-hole connect → 404 in 1–2 s; `LOCK TABLE` → 404 in 2.5–4 s; delay proxy 0.7 s + `LOCK TABLE` → 404 under 5 s; post-handshake stall → 404 under 5 s; remembered key + closed port → 503 `database: fail`; remembered key + `LOCK TABLE` → the probe runs (its own report, 200 expected); revoked while the database is up, then closed port → 404 (the `d` marker); the interleaving A/B race reproduced deterministically at the memory level (integration) and its HTTP consequence asserted (a remembered `v` older than a `d` never authorizes). Failing inputs, recorded in the commit bodies: the `roles` check removed → the non-admin case gets the probe body; the `is_blocked` check removed → the blocked-admin case gets it; the query wait's `stream_select` deadline removed → the post-handshake-stall case exceeds 5 s; the reserved Redis allowance removed (Redis skipped when the database phase used its allowance) → the remembered-monitor + `LOCK TABLE` case answers 404; the Lua CAS replaced by a plain `SET` → the older-write test overwrites the marker; the `at` freshness check removed → a 301-second-old `v` authorizes; the 404 body built differently on a lookup failure → the identical-body assertion fails.
10. **Logging and personal data.** Two `warning` records, `{exception}` only. The key, its hash and its prefix never appear in a log line, a response or an exception message the controller could echo. The authorizer never writes `last_used_at` — its statement is a `SELECT`.

## Applicability (high tier)

| Question | Applies? | Note |
|---|---|---|
| Crash before/after an external effect | yes | The only writes are the memory's CAS `EVAL`s. A crash between the database answer and the write leaves the memory one answer behind — stale by at most 300 s from that answer's `at` — and the next answer writes over it by the CAS; a crash between authorization and the probe costs one probe run. The database path is a `SELECT`. |
| Concurrent writers | yes | Concurrent requests race on the memory key; the CAS on the database's `answered_at` makes the memory converge to the *latest database answer* whatever the arrival order (finding 2's interleaving is the deterministic integration test). What the CAS cannot fix is a write that never reached Redis: a denied answer whose marker failed to land (Redis unavailable at that moment) leaves an older `v` in place until its `at` ages past 300 s — the admitted case, logged at `warning`, stated in the spec. |
| Money rounding | n/a | — |
| Empty/zero/null inputs | yes | No header, `Bearer` alone, a wrong-shaped key → refused before any I/O; `roles` without `ROLE_ADMIN` or malformed → denied; `expires_at` null → never expires; a memory value that is not the expected JSON → treated as not remembered; a remaining allowance of zero when a wait starts → the wait is not entered, the phase ends as unavailable. |
| Authorization boundary | yes | The only path into the `prod` probe: a database-verified unrevoked, unexpired key of an unblocked admin, or a `v` memory of exactly such a verification less than 300 s old while the database phase is unavailable; every refusal is the same 404; the firewall, voters and the API-key resource are untouched. Failing inputs in decision 9. |
| Deletion/expiry | yes | Revocation, expiry, blocking and demotion are denied answers that write a `d` marker — immediate while the database and Redis are up; during a database outage a `v` memory survives at most 300 s from its `at`; a deleted user cascades the key and the memory expires by TTL. |
| Idempotency of retries | yes | Every authorization is a read plus an idempotent CAS; a monitor retrying after a 404 changes nothing; the probe is read-only. |

## Risks / Trade-offs

- [A revoked monitor key keeps deep-probe access for ≤ 300 s from its last verification while the database is down, or when Redis was unreachable at the moment of the negative answer] → the price of a probe that can report the outage; bounded by the anchored lifetime; the probe is read-only diagnostics; stated in the spec and the how-to.
- [The probe's own checks still use the synchronous PDO and ext-redis clients with `statement_timeout`/read timeouts] → their responsive-server bounds hold (`HealthProbeTest`), but a lost response after the handshake would hang the *probe's* database check the same way it would have hung the authorizer; recorded here as the follow-up `AsyncPostgresQuery` makes possible (a small change: the check becomes `selectOne('SELECT 1')` under a 2-second deadline), deliberately not folded into this change's scope.
- [ext-pgsql joins the image and CI] → built from the libpq already present for pdo_pgsql; the only PHP client with a client-side read deadline; no Composer package.
- [Application and database clocks may differ] → the memory's lifetime is measured against the database's `answered_at`; NTP-close clocks shorten or lengthen the 300 s by the skew, never change which key is remembered.
- [Host-name resolution is outside the budget] → the same exclusion the probe already states; the how-to recommends IP literals or a local resolver for the two DSNs on hosts where the resolver may stall; the compose stack resolves service names locally.
- [Four short connections per authorized monitor poll] → negligible at a poll every 30–60 s; no pooling on purpose (a fresh connect is what observes a dependency that is down).
- [Fixture processes in the suite] → small single-file scripts, started per test, stopped in `finally`, ports from bind-to-0.

## Migration Plan

Image and CI: `pgsql` added to `install-php-extensions` and to `setup-php` extensions (rebuild the php image: `docker compose build php`, part of `make init`). Code only otherwise; a monitor sets `Authorization: Bearer <admin key>` on its deep-probe request and alerts on any non-200. Rollback: remove the code; `?deep=1` in `prod` is unconditionally 404 again; `probe-auth:*` keys expire within 300 s; the extension may stay.
