# Design — authorize-deep-probe-by-api-key

## Context

See `proposal.md` — Why. State: `HealthController` (`src/Shared/Health/`) answers `GET /health` (liveness) and `GET /health?deep=1` through `HealthProbe`, which deliberately builds its own raw clients from `DATABASE_URL` / `REDIS_URL` rather than the application's Doctrine connection or cache pool: a PDO with `ATTR_TIMEOUT` 2 s (pdo_pgsql maps it to libpq's `connect_timeout`) and `options='-c statement_timeout=2000'`, and an ext-redis client with 2-second connect and read timeouts; `HealthProbeTest` proves both bounds against a responsive server. In `prod` the controller returns a hand-built 404 problem body with `Cache-Control: no-store` for `?deep=1`. `/health` is `PUBLIC_ACCESS`, outside every firewall and the OpenAPI document. The archived change `add-api-keys-and-rate-limiting` left in `main`: `api_keys` (`key_hash` char(64) unique, `expires_at`, `revoked_at`, `user_id` → `users` with `roles` jsonb and `is_blocked`), `ApiKeyHeaderExtractor` (regex `^Bearer (lb_[A-Za-z0-9]{40})$`), `ApiKeyGenerator::hash()` (SHA-256 hex).

Constraints established by review (previous change's Gate 1 and this change's round 1 and confirmation 1): (1) no in-process PostgreSQL client PHP offers can be bounded by the caller through to *cleanup* — a synchronous PDO call blocks on a lost response; ext-pgsql's asynchronous API bounds the receive loop but its cancellation and close (`pg_cancel_query`, `pg_close`, the resource destructor) drain `PQgetResult` and therefore block on the same lost response (PHP 8.4 `ext/pgsql`, libpq asynchronous processing). (2) libpq's `connect_timeout` floor is 2 seconds. (3) Host-name resolution precedes every timeout and is bounded only by the resolver — the probe's existing contract already states this. (4) Ordering a memory by `clock_timestamp()` is unsound: the timestamp is evaluated when the expression runs, not when the statement's snapshot was taken, so a request paused between snapshot and evaluation can carry a stale row with a later time. (5) A reserved consultation allowance is needed for the outage report to be reachable (confirmed in confirmation 1).

What the runtime offers, verified in the container: `proc_open` is available (`pcntl` is not); Symfony `Process::checkTimeout()` calls `stop(0)` — SIGTERM, then SIGKILL immediately because the grace period is zero — and throws `ProcessTimedOutException` (`vendor/symfony/process/Process.php`); a console kernel boot costs ≈0.6 s in dev, so the child must not boot the kernel. ext-redis bounds each read with `OPT_READ_TIMEOUT` and the connect with the `connect()` timeout; Redis executes commands one at a time, so `INCR`/`EVAL` from concurrent clients are totally ordered. PostgreSQL READ COMMITTED takes a fresh snapshot per statement, and a single-statement autocommit `SELECT` sees every transaction committed before the statement started. The test suite runs the `prod` kernel through `HealthTest::bootProdKernel()`; the prod kernel reads `DATABASE_URL` without the `_test` suffix (the `app` database), which CI creates but does not migrate. Existing fixtures spawn helper processes (`tests/Fixture/consume-limiter.php`, `create-api-key.php`).

## Goals / Non-Goals

**Goals:** a `prod` deep probe a monitor can use; a verification whose worst-case duration — including whatever cleanup a stuck client needs — is enforced by a mechanism the caller controls; refusals that reveal nothing and cost nothing; a probe that still runs for a monitor verified before a database outage, with a memory whose ordering follows the *order in which answers were observed*, not clocks or snapshots, and whose failure modes are stated; every failure mode reproduced end to end through the `prod` kernel.
**Non-Goals:** see proposal. Design-level: no second authentication stack (only the extractor's regex and the hash function are reused); no ORM or cache component on this path; no configurability of the allowances or the TTL; the probe's own checks are not rewritten in this change (their lost-response gap is recorded in Risks as a follow-up candidate).

## Decisions

1. **`ProbeAuthorizer` outside the firewall.** `HealthController`, in `prod`, calls `ProbeAuthorizer::authorize(?string $authorizationHeader): bool` and runs the probe only on `true`; `false` keeps the existing 404 body. The authorizer matches the header against `ApiKeyHeaderExtractor`'s regex (no match → refusal before any I/O), hashes with `ApiKeyGenerator::hash()`, then runs the database phase (decision 3) and the memory phase (decision 4) under the allowances of decision 2. Alternatives rejected as before: `/health` under the firewall (liveness must stay open; the firewall's handler uses the unbounded ORM connection); the repository (unbounded).
2. **Two phases with fixed allowances.** `ProbeAuthorizer::DATABASE_ALLOWANCE = 2.5` s and `REDIS_ALLOWANCE = 1.0` s (reserved: the memory phase always gets it — confirmation 1, finding 3), 3.5 s of I/O in all; the refusal leaves within the spec's 5 seconds. Inside the Redis phase each operation (connect, `AUTH` when the DSN has a password, one command) gets `REDIS_ALLOWANCE / 3` as its connect or read timeout, so the phase cannot exceed its allowance even when every operation is slow. Host-name resolution is outside both allowances (Context, constraint 3); the how-to recommends IP literals or a local resolver for the two DSNs where the resolver may stall.
3. **The database phase is a child process killed at its deadline — `KeyLookupProcess`.** The lookup runs in `bin/probe-key-lookup`, a standalone PHP script (no kernel: `require vendor/autoload.php` for nothing but PDO is unnecessary — the script uses plain `PDO` and `getenv`), started by `Symfony\Component\Process\Process` with `setTimeout(DATABASE_ALLOWANCE)`, `DATABASE_URL` passed in the child's environment, the key hash written to the child's **stdin** (never argv or env — `ps` must not show it). The child connects with pdo_pgsql (`ATTR_TIMEOUT` 2 s, `statement_timeout` = the allowance in ms as the belt), runs one statement — `SELECT u.roles, u.is_blocked, k.revoked_at, k.expires_at FROM api_keys k JOIN users u ON u.id = k.user_id WHERE k.key_hash = :hash` — and prints exactly one line: `V <expires_at RFC 3339 or ->` (verified: row present, `revoked_at IS NULL`, not expired at the child's `now`, `is_blocked = false`, `roles` contains `ROLE_ADMIN`), `D` (denied: no row, or a row failing a condition — the database *answered*), or `U <exception class>` (unavailable: connect or query failed). The parent maps the exit: a clean `V`/`D`/`U` line → that outcome; a `ProcessTimedOutException` (the child was SIGKILLed with its blocked libpq call, its socket closed by the kernel — no PHP cleanup runs in the parent), a non-zero exit, or unparsable output → **unavailable** with a `warning` "deep probe authorization: database unavailable" `{reason class}`. This is the only mechanism in PHP that bounds the *whole* operation including a stuck client's teardown: the operating system reclaims the process. Cost: one `proc_open` and a ≈20-ms PHP start per monitor poll, without a kernel boot. Alternative — ext-pgsql's asynchronous API — rejected (Context, constraint 1: cleanup blocks on `PQgetResult`). Alternative — a hand-written wire-protocol client over PHP streams — rejected: SCRAM authentication and protocol handling are security-sensitive code with no portfolio value. Alternative — `pcntl_alarm` — unavailable under FPM.
4. **`ProbeMemory` ordered by a generation counter, not by time.** Redis holds, per key hash `h` (`sha256(h)` in the key names): `probe-auth:gen:<h>` — an integer incremented (`INCR`, 300-second TTL refreshed) on **every denied answer** — and `probe-auth:v:<h>` — a JSON `{"gen":<g>,"exp":<expires_at or null>}` written by one Lua script (`EVAL`) that stores it **only if `g` equals the current generation** (absent counts as 0), with a 300-second TTL. The authorizer reads the generation **before** the database phase (`GET probe-auth:gen:<h>` → `g₀`, absent → 0) and, after a verified answer, writes `{gen: g₀, exp}` through the CAS. Ordering argument (confirmation 1, finding 2): a stale verification is one whose statement snapshot predates a revocation R; a denial D observed R happens after R and does `INCR` after its own statement; our verified request read `g₀` *before* its statement started, so its statement's snapshot is later than that read; if D's `INCR` happened before our `GET`, our snapshot is later than R and we would have read the revocation ourselves (contradiction); therefore D's `INCR` happened after our `GET` and the current generation at our write is ≥ g₀ + 1 ≠ g₀ → the CAS refuses the stale `v`. Redis executes the commands of all clients in one total order, and READ COMMITTED gives each statement a snapshot no older than the statement's start — the two facts the argument uses, both verified in Context. **Consult** (only when the database phase is unavailable): `GET probe-auth:v:<h>` → authorize iff present and `exp` is null or in the future by the request's clock (expiry keeps applying during an outage). No comparison of `gen` at consult time: a `v` present in Redis is one that no denial has superseded (a denial would have advanced the generation, and the next verified write would need the new one; the old `v` is *not* deleted by the denial — so the denial also does `DEL probe-auth:v:<h>`, which is safe here because `DEL` after `INCR` cannot be undone by a late stale write). Every Redis failure → `warning` "deep probe authorization: memory unavailable" `{exception class}` and counts as "not remembered"/"not written". **Admitted case (unchanged):** if Redis is unreachable at the moment of a denial, neither `INCR` nor `DEL` lands and an earlier `v` survives up to its 300-second TTL — stale authorization during a database outage bounded by that TTL, stated in the spec, logged at `warning`. Alternative — ordering by `clock_timestamp()` — rejected (constraint 4). Alternative — a `revision` column on `api_keys` and `users` — rejected: two schema changes and two row versions with no total order between them, when the order Redis already provides is exactly the order the memory needs.
5. **The outage report is the probe's own.** When a remembered monitor is authorized during database unavailability, the probe runs unchanged and reports what *it* observes: a refused or unreachable database → `503` with `database: fail`; a database that answers `SELECT 1` but had `api_keys` locked or a lookup that stalled → possibly `database: ok`. The spec promises "the probe runs and reports its own checks", not a status.
6. **Refusals are one body.** The controller keeps the existing 404 problem body and `Cache-Control: no-store` for every `false`; no `WWW-Authenticate`, no `Retry-After`. The reason exists only in the `warning` and in the tests' timing assertions.
7. **Fixtures** (`tests/Fixture/`): `black-hole-socket.php` (binds 127.0.0.1:0, prints the port, accepts, never writes — a connection that never completes); `tcp-proxy.php` (binds 127.0.0.1:0, prints the port; `--upstream=host:port`, `--delay=<s>` before connecting upstream, `--stall-after-responses=<n>` forwards upstream→client for the first *n* upstream messages then swallows everything upstream sends while still forwarding client→upstream — a completed handshake followed by a lost response); `fake-redis-server.php` (binds 127.0.0.1:0, prints the port; speaks enough RESP to answer `AUTH` with `+OK`, `GET` with `$-1`, `INCR` with `:1`, `EVAL` with `+OK`, each after `--response-delay=<s>` — a Redis whose every operation is slow, for cumulative-timeout tests with a password in the DSN). All run with `Process`, stopped in `finally`, ports from bind-to-0. A stalled *statement* on a responsive server is `LOCK TABLE api_keys IN ACCESS EXCLUSIVE MODE` in an open transaction on the test's own connection. The prod kernel under test reads `DATABASE_URL`/`REDIS_URL` from `$_SERVER`/`$_ENV`, set for that kernel and restored (the `bootProdKernel` pattern).
8. **Prod-kernel tests need the schema in `app`.** `HealthDeepProdTest` inserts the admin user and keys into the `app` database through a bounded PDO of its own (committed, removed in `finally`); CI gains `make migrate EXEC=` before `make test-db EXEC=`.
9. **Tests.** *Unit*: `ProbeAuthorizer` with the two phases faked — verified → true + remember(g₀); denied → false + `INCR` + `DEL`; unavailable + `v` present and unexpired → true; unavailable + `v` expired by `exp` → false; unavailable + no `v` → false; unavailable + Redis failing → false; a non-key header → false with no I/O; a database phase reported as timed out still consults the memory; `KeyLookupProcess` output parsing (`V …`, `D`, `U …`, garbage → unavailable). *Integration* — `KeyLookupProcessTest` (real PostgreSQL + fixtures): admin key → `V` with the key's expiry; non-admin / blocked / revoked / expired / unknown → `D`; closed port → `U` at once; black-hole connect → `U` within the allowance (the child killed at 2.5 s, or libpq's 2-second connect timeout first); `LOCK TABLE` → `U` at the allowance with the child killed and no lingering process (`ps` shows no `probe-key-lookup` after the call); proxy `--stall-after-responses=1` (handshake done, response lost) → `U` at the allowance, child killed — the case no in-process client passes; the hash is not in the child's command line (`ps` on the running child during the `LOCK TABLE` case shows no hash). `ProbeMemoryTest` (real Redis): `remember(g)` stores only when `g` is current; `deny` increments the generation and deletes `v`; the interleaving **established by the real mechanism**: connection A `GET gen` (0), A's `SELECT` on a fresh connection while the key is valid (autocommit, so the snapshot is taken now), then revoke the key in the database, then a full `authorize()` as B (denied → `INCR` → 1, `DEL`), then A continues with `remember(gen 0)` → refused, `v` absent → a later closed-port outage refuses the monitor — no timestamps supplied; TTL ≤ 300 s; the fake Redis with `--response-delay=0.25` and a password → `AUTH` + `GET` + `EVAL` all succeed within the phase (3 × 0.25 < 1.0), with `--response-delay=0.5` → the second operation's read times out and the phase ends as "memory unavailable" within its allowance. `ProbeAuthorizerTest` (real PostgreSQL and Redis, spy logger): admin key → true and `v` present; non-admin / blocked / revoked / expired / unknown → false, generation advanced, `v` absent; closed port → false within 3 s with the "database unavailable" warning; `LOCK TABLE` → false within 3 s; a remembered `v` + closed port → true; after a denial + closed port → false; Redis unreachable during a denied answer → false, the "memory unavailable" warning, and the earlier `v` still present (the admitted case, asserted as such). *Api* (`HealthDeepProdTest`, prod kernel): the refusal matrix with identical bodies and unchanged `last_used_at`; admin key → probe body; closed port → 404 under 1 s; black-hole connect → 404 under 3.5 s; `LOCK TABLE` → 404 in 2.5–4 s; proxy `--delay=0.7` + `LOCK TABLE` → 404 under 5 s; proxy `--stall-after-responses=1` → 404 under 5 s; database closed + fake Redis with `--response-delay=0.5` → 404 under 5 s; remembered key + closed port → 503 `database: fail`; remembered key + `LOCK TABLE` → the probe runs (200 expected); revoked while the database is up, then closed port → 404. Failing inputs, recorded in the commit bodies: the `roles` check removed → the non-admin case gets the probe body; the `is_blocked` check removed → the blocked-admin case gets it; `setTimeout` removed from the child process → the lost-response case exceeds 5 s (the parent waits on the child); the generation read moved *after* the database phase → the established-interleaving test stores the stale `v`; the CAS replaced by a plain `SET` → the same test stores it; `DEL` on denial removed → the "after a denial + closed port" case authorizes; the `exp` check at consult removed → an expired remembered key authorizes; the reserved Redis allowance replaced by "skip when the database phase used its allowance" → the remembered-monitor + `LOCK TABLE` case answers 404; the 404 body built differently on a lookup failure → the identical-body assertion fails.
10. **Logging and personal data.** Two `warning` records, `{exception}` (or the child's failure class) only. The key, its hash and its prefix never appear in a log line, a response, the child's command line or an exception message the controller could echo. The authorizer never writes `last_used_at` — the child's statement is a `SELECT`.

## Applicability (high tier)

| Question | Applies? | Note |
|---|---|---|
| Crash before/after an external effect | yes | The only writes are Redis `INCR`/`DEL` (denial) and the CAS `EVAL` (verification). A crash between the database answer and the write leaves the memory one answer behind — a missed denial's `INCR`/`DEL` is the admitted staleness (≤ 300 s TTL); a missed verification write only delays the memory. A child killed at its deadline leaves no state (a `SELECT`). |
| Concurrent writers | yes | Requests race on the two Redis keys; Redis totally orders their commands, and the generation read *before* each request's statement makes a stale verification's write fail the CAS whenever a denial was observed between (decision 4's argument, tested by the established interleaving). What no ordering fixes is a write that never reached Redis — the admitted case, logged and bounded. |
| Money rounding | n/a | — |
| Empty/zero/null inputs | yes | No header, `Bearer` alone, a wrong-shaped key → refused before any I/O; `roles` without `ROLE_ADMIN` or malformed → `D`; `expires_at` null → never expires (`exp` null in the memory); a child that prints nothing, garbage or exits non-zero → unavailable; a memory value that is not the expected JSON → not remembered. |
| Authorization boundary | yes | The only path into the `prod` probe: a database-verified unrevoked, unexpired key of an unblocked admin, or a `v` memory of such a verification that no later denial superseded and whose expiry has not passed, while the database phase is unavailable; every refusal is the same 404; the firewall, voters and the API-key resource are untouched; the hash never reaches a command line. Failing inputs in decision 9. |
| Deletion/expiry | yes | Revocation, blocking and demotion are denied answers that advance the generation and delete `v` — immediate while the database and Redis are up; expiry is checked from `exp` at consult time even during an outage; a deleted user cascades the key and the memory expires by TTL. |
| Idempotency of retries | yes | Every authorization is a read plus idempotent Redis writes; a monitor retrying after a 404 changes nothing; the probe is read-only. |

## Risks / Trade-offs

- [A revoked monitor key keeps deep-probe access for ≤ 300 s while the database is down, when Redis was unreachable at the moment of the denial] → the price of a probe that can report the outage; bounded by the TTL; the probe is read-only diagnostics; stated in the spec and the how-to.
- [The probe's own checks still use synchronous clients] → their responsive-server bounds hold (`HealthProbeTest`); a lost response after the handshake would hang the probe's database check; recorded as a follow-up (the check can run through `KeyLookupProcess`'s sibling — a `SELECT 1` child with the same kill deadline), deliberately not folded into this change.
- [A process spawn per monitor poll] → ≈20 ms of PHP start without a kernel, every 30–60 s; `proc_open` must be allowed in the deployment's PHP configuration (it is in the image; the how-to says so).
- [The child is killed with a blocked libpq call] → the kernel closes its socket; PostgreSQL notices the dead client at the next write or by TCP keepalive and ends the session — no lock is held (a `SELECT` without `FOR …`).
- [Host-name resolution is outside the allowances] → the probe's existing exclusion; the how-to recommends IP literals or a local resolver.
- [Fixture processes in the suite] → small single-file scripts, started per test, stopped in `finally`, ports from bind-to-0.

## Migration Plan

Code only (no schema change, no new extension): `bin/probe-key-lookup` ships with the code and must be executable; a monitor sets `Authorization: Bearer <admin key>` on its deep-probe request and alerts on any non-200. Rollback: remove the code; `?deep=1` in `prod` is unconditionally 404 again; `probe-auth:*` keys expire within 300 s.
