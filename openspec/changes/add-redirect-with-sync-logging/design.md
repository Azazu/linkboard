# Design — add-redirect-with-sync-logging

## Context

See `proposal.md` — Why. State: `links` exists with `click_count`, `max_clicks`, `expires_at`, `is_active`, `utm` and an exact-match `findBySlug`; two firewalls (`api` stateless JWT, `main` lazy session); a per-IP auth limiter on a Redis pool with a Redis lock and an in-memory storage in tests; problem-details responses for the API; `TRUSTED_PROXIES` configured; `src/Redirect/` and `src/Click/` are empty placeholders. Constraints: DataMapper entities, thin controllers, CQRS-lite (the click write path never shares entities with reads), no new dependency, the `ClickRecorder` seam must survive `add-async-click-logging` unchanged from the controller's point of view.

## Goals / Non-Goals

**Goals:** a correct, testable baseline of the redirect with an exact click limit; a write-path seam that stage 2 swaps without touching the controller or the specs' observable behavior; four small error pages; the two env variables.
**Non-Goals:** see proposal. Design-level: no Redis for link resolution or click counting yet (the only Redis use on the hot path is the rate limiter, fail-open — decision 9), no caching of link rows (row 7 decides), no entity hydration for clicks, no availability during a total database outage (decision 13).

## Decisions

1. **Route placement and firewall** — `#[Route('/{slug}', requirements: ['slug' => '[A-Za-z0-9_-]{3,32}'], methods: ['GET', 'HEAD'], priority: -100)]` on `RedirectController` (`src/Redirect/`). It must stay under the `main` firewall (lazy) for every valid slug: today's `api` firewall pattern `^/api` also captures slugs such as `api-promo` (reserved words are exact matches only), which would run them through JWT authentication and turn an invalid bearer into 401. The pattern becomes `^/api(/|$)` so that `/api`, `/api/...` keep the stateless firewall and `/api-anything` falls through to `main`; `access_control` already uses slash-anchored `^/api/` patterns and `^/api/v1$`, and `^/health` is tightened to `^/health$` for the same reason. Under `main`, no `access_control` line matches `/{slug}`, so access is granted, and the controller never reads the token, so no session starts and no cookie is set (asserted by a web test, including an `api`-prefixed slug with no and with an invalid bearer, and `/api/v1/me` still 401). Alternative — a dedicated `security: false` firewall for slugs — rejected: its pattern would have to exclude every reserved word, duplicating `ReservedSlugs`. The lowest priority makes every attribute and YAML route win over the slug even though reserved words cannot be slugs; `debug:router` is checked in a task.
2. **Thin controller, one use case** — `RedirectController` does HTTP only: rate-limit check (decision 9), header bounds (decision 8), calls `RedirectResolver::resolve(slug, Visit)` and maps the returned `RedirectDecision` (`notFound | gone | unavailable | redirect(location)`) to a `Response`, adding `Cache-Control: no-store` to all and `Referrer-Policy` to the 302. `Visit` is a small readonly DTO (client IP, truncated UA, truncated Referer, `occurredAt`, `isHead`). `RedirectResolver` (application service): `findBySlug` (1 SELECT; a failure here → decision 13) → 404 when null or inactive → 410 when expired or `click_count >= max_clicks` (fast path, no write) → `HEAD`: `redirect(location)` without recording → else `ClickRecorder::record(link, visit)` → `allowed` → 302, `exhausted` → 410, write failure → decision 5.
3. **Exact limit = one conditional UPDATE** — `DbalClickRecorder::record()` runs, in one DBAL transaction: `UPDATE links SET click_count = click_count + 1 WHERE id = :id AND (max_clicks IS NULL OR click_count < max_clicks)`; 0 rows → `exhausted` (no insert); 1 row → `INSERT INTO clicks (...)`; commit. The row lock taken by the UPDATE serialises concurrent requests, so the count can never pass `max_clicks` (spec redirect, "exact under concurrency"; integration test with parallel connections). It guarantees nothing when the database is unreachable — that is decision 5's job. Alternatives: `SELECT … FOR UPDATE` + separate UPDATE (two statements, longer lock), optimistic version column with retries (loops under contention) — rejected. The PHP pre-check in decision 2 is an optimisation for already-exhausted links, never the authority.
4. **DBAL write path, read-only entity** — the hot path uses `Connection` directly (no UnitOfWork, no hydration); `src/Click/Entity/Click.php` is `#[ORM\Entity(readOnly: true)]` and exists so that `doctrine:schema:validate`, `make migration` and tests know the table (§3.4 columns, `idx_clicks_link_occurred` index, partial index `WHERE NOT is_bot`, FK `ON DELETE CASCADE`). `ClickRecorderInterface` (`src/Click/`) with `record(Link, Visit): RecordOutcome` is the seam row 7 re-implements with dispatch + Redis counter. `links.click_count` is written by SQL only; the `Link` entity keeps no setter for it (consistent with `add-link-crud` decision 1).
5. **Click-write failure policy** — bounded to failures of `record()` after the link was resolved (a lookup failure is decision 13). `RedirectResolver` wraps `record()` in `try/catch (\Throwable)`: link without `max_clicks` → log `error` (`{link_id, exception: class}` — no IP, UA or URL) and return `redirect(location)` — the one case in which a GET 302 leaves no click, stated as such in both specs; link with `max_clicks` → log `warning` and return `unavailable` (503, `Retry-After: 5`). `HEAD` never calls `record()`, so it answers from the link state and is unaffected (spec redirect, HEAD scenario). This is the synchronous form of FR-RED-4/FR-RED-3/NFR-REL-1 and the seam keeps it when the recorder becomes asynchronous. Not guaranteed: a crash after the commit and before the response leaves one counted click without a delivered redirect (at most one per crash; stated in the spec). Tested by swapping the recorder for a throwing stub in the test container (`disableReboot`); what that stub proves is the resolver's reaction to a write failure, not behavior during a PostgreSQL outage (decision 13).
6. **UTM composition** (`src/Redirect/UtmAppender`, pure function) — never `parse_str`/`http_build_query` (they collapse repeated keys and rewrite `a.b` to `a_b`). Split the target once at `#` (fragment kept verbatim) and once at the first `?`; split the raw query on `&`; for each pair take the part before the first `=` as the raw key and compare `rawurldecode(key)` with the link's UTM key names; drop matching pairs (every occurrence, every spelling), keep all others byte for byte and in order; append `key=rawurlencode(value)` for the link's UTM keys in the fixed order `utm_source, utm_medium, utm_campaign, utm_term, utm_content`; reassemble `base?query#fragment` (omit `?` when the query ends up empty). Operates only on targets already accepted by `TargetUrlPolicy`, which rejects control characters and backslashes, so no CR/LF can reach the header; `RedirectResponse` would reject them anyway. Unit matrix: repeated keys, dotted keys, bracket notation, encoded key and value spellings, empty query, existing fragment.
7. **Visitor hash and referer host** (`src/Click/VisitorHasher`, `src/Click/RefererHost` — in Click, not Redirect: `referer_host` is a click column and Click must not depend on Redirect) — `hash('sha256', $salt."\0".$ip."\0".$ua)` with `VISITOR_HASH_SALT` injected via `%env(VISITOR_HASH_SALT)%` (the NUL separators make the concatenation of FR-CLK-2 unambiguous; documented). `RefererHost::of(?string)` (own host from `APP_PUBLIC_URL`): null when the header is absent or contains a control character (checked on the raw header — `parse_url` would rewrite it to `_`), else `parse_url` host, lower-cased, then validated against the column — null when unparseable, longer than 255 bytes, not valid UTF-8 (`mb_check_encoding`), or equal to the own host (same-origin). The bound on the whole header (decision 8) limits work; this bound protects the INSERT, so a hostile `Referer` can never fail or lose a click (spec click-logging, "Hostile referer host").
8. **Header bounds** — `substr(UA, 0, 1024)`, `substr(Referer, 0, 2048)` in the controller before building `Visit`; `Accept-Language` is not read in this change. A truncated Referer that no longer parses yields `referer_host` null, never an error.
9. **Rate limiter `redirect_ip`, fail-open** — `framework.rate_limiter.redirect_ip`: `sliding_window`, `limit: '%env(int:RATE_LIMIT_REDIRECT_PER_IP)%'`, `interval: '1 minute'`, `cache_pool: cache.rate_limiter`, `lock_factory: lock.factory`; `when@test` → `storage_service: app.rate_limiter.test_storage` (same reasons as `auth_ip`: pools reset between requests). This is the only Redis use on the hot path (storage and lock), and the installed `SlidingWindowLimiter::reserve()` acquires the lock and reads storage without converting failures into a rate-limit result, so a Redis outage would throw before any redirect. `src/Redirect/RedirectRateLimit` wraps the whole `create(ip)->consume()` expression — creation and consumption, since the lock acquisition and the storage reads/writes happen inside `consume()` — in one `try/catch (\Throwable)` and returns `allowed | limited(retryAfter)` (`RateLimitVerdict`); a failure is logged there at `warning` `{exception: class}` (no IP) and reported as allowed, so the controller has one branch. Guarantee boundary: the limit holds exactly while Redis (storage and lock) is reachable; during an outage redirects are unlimited — availability over throttling (NFR-REL-1), stated in the spec and the how-to. Alternative fail-closed (503 for everyone while Redis is down) — rejected: it would make the whole service depend on Redis. Alternative — a kernel subscriber like `AuthRateLimitSubscriber` — rejected: that one exists to run before the firewall and password hashing; here the controller is the first cost. Key = `Request::getClientIp()` (trusted proxies, FR-KEY-5). Tested with three stubs installed through the test container in place of `limiter.redirect_ip`: a factory that throws on `create()`; a factory returning a real `SlidingWindowLimiter` whose `LockFactory` uses a store that throws on `save()` (lock acquisition fails inside `consume()`); and one whose `StorageInterface` throws on `fetch()`/`save()` (storage fails inside `consume()`). Moving `consume()` outside the catch keeps the first test green and fails the other two — that is the failing input.
10. **Problem details helper moves to Shared** — `App\Shared\Api\ProblemDetails::response(int $status, string $title, string $detail): JsonResponse` (body and headers exactly as today's `JwtProblemDetailsSubscriber::problem`); the auth subscribers delegate to it. Content negotiation: `Accept` contains `application/json` → problem details, else Twig page (`templates/redirect/{not_found,gone,rate_limited,unavailable}.html.twig`, extending `base.html.twig`). 404/410/429/503 are returned by the controller, not thrown, so the framework's error renderer and its default headers never apply.
11. **Migration** — `make migration` after the entity mapping, then reviewed: table `clicks` per §3.4 (`id uuid PK`, `link_id uuid FK → links ON DELETE CASCADE`, `occurred_at timestamptz NOT NULL`, `country char(2)`, `device_type varchar(16)`, `os varchar(16)`, `browser varchar(32)`, `is_bot boolean NOT NULL DEFAULT false`, `referer_host varchar(255)`, `visitor_hash char(64) NOT NULL`, `variant varchar(16)`, `resolved_by varchar(8) NOT NULL`), index `(link_id, occurred_at)` (ascending — a btree serves `ORDER BY … DESC` by backward scan and Doctrine does not model sort order), partial index `(link_id, occurred_at) WHERE NOT is_bot`, the FK's own `link_id` index Doctrine maintains, `getDescription()`, reversible `down()`.
12. **Configuration** — `.env`: `RATE_LIMIT_REDIRECT_PER_IP=60`, `VISITOR_HASH_SALT=localdev-only-salt-override-in-env-local` with a comment; `.env.test`: a fixed `VISITOR_HASH_SALT`; CI: the `.env` default suffices (tests assert stability and difference, not a specific digest). The production value is referenced by name only (AGENTS.md secrets rule).

13. **Link lookup failure** — `findBySlug` runs before any catch of decision 5 and shares PostgreSQL with the click store; when it throws (connection refused, statement error) nothing can be resolved: `RedirectResolver` catches it separately, logs `error` `{slug_length, exception: class}` (no slug value — it is user data), and returns `unavailable` (503, `Retry-After: 5`) for every slug. No availability during a total database outage is claimed by this change; a link cache that could serve redirects through an outage is row 7's decision. Tested by replacing `LinkRepositoryInterface` with a throwing stub in the test container. The write-failure scenarios of decision 5 are therefore explicitly bounded to "link resolved, click write failed" — which is what the throwing recorder reproduces.

## Applicability (high tier)

| Question | Applies? | Note |
|---|---|---|
| Crash before/after an external effect | yes | the only effect is the DB transaction (UPDATE + INSERT); a crash before commit leaves nothing, a crash after commit and before the response leaves one counted click without a delivered redirect (decision 5, bounded to one per crash, stated in the spec); a lookup failure before any effect → 503 (decision 13); a limiter-store failure → fail-open (decision 9); logging happens after the outcome is known |
| Concurrent writers | yes | N concurrent redirects on one limited link: the conditional UPDATE takes the row lock, so exactly `max_clicks` requests get 1 affected row (decision 3); test 1.4(d) with separate connections; the PHP pre-check is never the authority |
| Money rounding | n/a | |
| Empty/zero/null inputs | yes | absent/oversized UA and Referer → truncated, never an error (decision 8); unparseable, overlong (> 255 bytes), non-UTF-8 or control-character Referer host → `referer_host` null, click still stored (decision 7); link without UTM → target unchanged; target query with repeated/dotted/bracketed/encoded keys preserved verbatim (decision 6); `max_clicks` null → unconditional increment; empty `Accept` → HTML |
| Authorization boundary | yes | the endpoint is public by design: no token is read, no session started, no cookie set (decision 1, asserted); the `api` firewall pattern is narrowed to `^/api(/|$)` so `api`-prefixed slugs never meet JWT authentication while `/api/...` keeps it (asserted both ways); it exposes nothing beyond the 302/404/410 the link owner configured; the API keeps its own voters |
| Deletion/expiry | yes | expired link → 410 at request time, never a job; deleting a link cascades to `clicks` (FK); a redirect racing a delete gets 404 (row gone) or a recorder failure → decision 5 |
| Idempotency of retries | yes | a client retry is a new visit and a new click by definition; `HEAD` records nothing; the recorder's UPDATE + INSERT is one transaction so a failed attempt leaves no half-click (test 1.4(c)) |

## Risks / Trade-offs

- [Hot links contend on the `links` row lock: 1 SELECT + 1 UPDATE + 1 INSERT per redirect] → accepted as the stage-1 baseline; row 7 removes the SQL write from the hot path and moves the limit to Redis; the how-to names the deviation from FR-RED-2 explicitly.
- [The committed salt default is public] → it is a local-development default like the DB password; production must set `VISITOR_HASH_SALT` in `.env.local`/CI (how-to), and a rotation note explains the lost continuity.
- [Per-IP limit penalises users behind one NAT] → default 60/min is the specification's value and is configurable; API-key limits (row 10) will not affect redirects.
- [A slug that equals a future top-level route] → `ReservedSlugs` is compared with the router by an existing test (`ReservedSlugsCoverRoutesTest`); the redirect route's `-100` priority means a new page always wins over an old slug.
- [Throwing-stub tests do not exercise a real outage] → each stub proves one reaction: lookup failure → 503 (decision 13), write failure → 302/503 (decision 5), limiter failure → fail-open (decision 9); the integration test of the recorder covers the SQL; a real outage of PostgreSQL hits the lookup first and is therefore a 503 for every slug, which the specs now say.
- [Fail-open rate limiting during a Redis outage] → accepted trade-off: the alternative makes redirects depend on Redis; the outage is logged at `warning` on every request and Redis AOF persistence plus the health endpoint make it visible.
- [Narrowing the `api` firewall pattern changes security configuration] → the change is one regex with an explicit test in both directions (`/api-promo` public, `/api/v1/me` still 401); flagged as security-sensitive in the commit body and the handoff.

## Migration Plan

`make migration` → review the class → `make migrate` → `make test-db`. Rollback: `doctrine:migrations:migrate prev` drops `clicks` (no data worth keeping in stage 1). Deploy order: migration, then code (the code writes to the new table).
