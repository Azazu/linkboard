## Context

See `proposal.md` — Why. What shapes the approach is what the document already contains and how it is produced.

- `GET /api/docs.json` is generated by API Platform 4 from the resource attributes. Measured on the current `main`: 25 operations, every one with a description; response statuses present are 200, 201, 204, 400, 403, 404 and 422; **401, 406, 409 and 429 appear nowhere**; every error response lists `application/json` next to `application/problem+json`; no operation carries an example.
- The collections already declare their filters and ordering as parameters (`isActive`, `slug`, `order[createdAt]`, `order[clickCount]`, `page`, `itemsPerPage`) — through `OpenApiOperation(parameters: …)` on `LinkResource`. There is nothing to add there, only something to verify.
- The error body is produced by API Platform's normalizer and, off the resource paths, by `src/Shared/Api/ProblemDetails.php`; both use `type` = `/errors/<status>`.
- The document can be decorated: `ApiPlatform\OpenApi\Factory\OpenApiFactoryInterface` is a single-method service, and `ApiPlatform\OpenApi\Model\Response` is an immutable value with `description`, `content` and `headers`.

## Goals / Non-Goals

**Goals**

- A document that states what each operation can answer, checked against what it does answer.
- One place that knows the common error responses, so a new operation inherits them instead of being remembered.
- Examples that cannot contradict the schema they illustrate.

**Non-Goals** (beyond the proposal's)

- Editing responses per operation by hand where a rule can decide them: 25 operations times four statuses is 100 places to be wrong.
- Generating the error catalogue from code. It is prose about meaning and recovery, which no generator can write; what is generated is the *check* that it is complete.

## Decisions

### 1. The common error responses come from one decorator, not from 25 attributes

A decorator over `OpenApiFactoryInterface` walks the generated document and adds, to each operation, the failure responses that operation's own path implies: 401 where the path is behind a firewall, 429 where the rate limiter covers it, 406 where a client can ask for a media type the operation does not produce. It also replaces every error response's content with the single problem-details media type.

*Why:* the rules that decide these are global — the firewall map, the limiter's paths, the one error format — so they belong in one place that reads them, not restated as attributes on every operation. A new resource then arrives documented correctly without anyone remembering to.

*Alternatives.* (a) `openapi: new OpenApiOperation(responses: …)` on every operation: a hundred hand-written entries that drift the first time a firewall changes. Rejected. (b) A static YAML overlay merged into the document: the same duplication, now in a second language and unable to see the firewall configuration. Rejected.

*What this does not guarantee:* the decorator adds what the *path* implies. A refusal specific to one operation — the 409 when an account is at its active-key cap — is declared on that operation, because only it knows.

### 2. The rules the decorator applies are read from configuration, not copied into it

Which paths are public and which are rate-limited already exists — in `config/packages/security.yaml`'s access control and in the limiter's own configuration. The decorator takes the same patterns as parameters from the service container rather than repeating them as literals.

*Why:* a rule repeated is a rule that drifts. This is the defect class row 11's Gate 1 found in a path pattern, and the process's own "fix the claim, not the line".

*What this does not guarantee:* the decorator matches paths; it does not evaluate the security expression of an operation. An operation that is public but sits under a guarded prefix would be documented as refusable — there is none today, and a test names the public paths so that a future one is caught rather than silently mis-documented.

### 3. Examples are declared per property, once

Representative values go on `ApiProperty(example: …)` on the resources and input DTOs; API Platform composes them into the schemas, which every operation using that resource then shows. No operation carries a hand-written example body.

*Why:* an example that lives beside the property it illustrates is checked by the same schema the property is checked by, and one field's example is written once no matter how many operations expose it.

*What this does not guarantee:* an example is a plausible value, not a fixture — nothing asserts that the exact example would survive a real write. The contract tests exercise real requests; the examples illustrate.

### 4. The contract tests compare the document with behaviour, not with itself

`tests/Api/Contract/` reads the generated document once, then for a table of representative requests — one per operation, plus an anonymous call, an authorization refusal, a validation refusal and a rate-limit refusal — asserts that the status returned is declared for that operation and that the response's media type is the one documented for that status.

*Why:* this is the only assertion that makes the document worth trusting. Reading the document and asserting things about its own shape proves nothing an integrator cares about.

*What this does not guarantee:* it is a representative sample, not an exhaustive one — it cannot prove the API never answers an undocumented status, only that the answers it was asked for are documented. The rate-limit case is exercised where the limiter can be driven within a test; where it cannot, the test says so rather than pretending.

### 5. The catalogue is prose, its completeness is a test

`docs/reference/api-errors.md` explains each error type and its recovery. A test enumerates the types the code can produce — the statuses the document declares, plus what `ProblemDetails` can emit — and fails when one is missing from the catalogue.

*Why:* the risk with a hand-written catalogue is not that it is wrong on the day it is written but that it is incomplete a change later. The test is what makes it stay true.

## Risks / Trade-offs

- **A decorator that rewrites responses could hide a real response** → it only adds statuses and narrows error media types; a test asserts that every response the ungenerated document carried is still present, so nothing is lost by the rewrite.
- **Documented-but-unreachable statuses** → the opposite error of today's, and equally a lie. The path rules are narrow (a firewall, a limiter, content negotiation), and the contract tests exercise each added status at least once somewhere in the suite.
- **The examples become stale** → they live on the property whose schema constrains them, and a changed type or constraint puts the example next to the change.
- **The contract suite grows slow** → it makes one request per operation against the test kernel, like the existing `tests/Api` suites, and reads the document once per class rather than per test.

## Migration Plan

No migration: no schema change, no data change, and no change to what any endpoint answers. The document changes shape on deploy — new statuses, one media type per error, examples — which is additive for a client reading it and corrective where it was wrong. Rolling back is reverting the merge.
